# 1. Module Component Design

## Purpose

This document defines the internal module decomposition of the MBB ya Kin system. It specifies each of the 9 modules, their responsibilities, inputs/outputs, dependencies, and interaction patterns. This is the foundation for implementation—each module maps to one FastAPI service or Celery task component.

## Audience

- **Backend Developers**: Implement modules M1–M9 according to these specifications
- **Architecture Reviewers**: Validate module boundaries and dependency graph
- **Integration Engineers**: Connect modules via Celery task orchestration layer
- **QA/Testing**: Use module interface specs to design integration tests

---

## 1. Module / Component Design

#### M1: WhatsApp Gateway Module

**Layer:** Interaction  
**Responsibility:** Receive inbound WhatsApp messages via a dual-mode channel adapter (Baileys bridge for dev/testing, WhatsApp Business API webhook for production), normalize them into a standard internal format, and dispatch outbound responses back through the active WhatsApp transport.

**Inputs:**
| Input | Source | Format |
|-------|--------|--------|
| Raw WhatsApp webhook payload (production) | WhatsApp Business API (HTTP POST) | JSON (WhatsApp Cloud API schema) |
| Raw WhatsApp webhook payload (dev/testing) | Baileys Node.js bridge (HTTP POST) | JSON (Baileys event schema) |
| Outbound response content | Conversation Engine (M4) | `OutboundMessageDTO` |

**Outputs:**
| Output | Destination | Format |
|--------|-------------|--------|
| Normalized inbound message | Message Queue (M3) | `InboundMessageEvent` |
| WhatsApp send request (production) | WhatsApp Business API (HTTP POST) | JSON (WhatsApp send message schema) |
| WhatsApp send request (dev/testing) | Baileys bridge HTTP API | JSON (Baileys send schema) |
| Delivery status acknowledgment | WhatsApp API or Baileys bridge | HTTP 200/202 |

**Internal Logic:**
1. **Webhook Reception (Dual-Mode):**
   - **Production mode** (`WHATSAPP_MODE=official`): Accept POST from WhatsApp Business API (`/api/v1/messages`), validate JWT auth header.
   - **Dev/Testing mode** (`WHATSAPP_MODE=baileys`): Accept POST from Baileys bridge (`/api/v1/messages/baileys`), validate shared webhook secret via `X-Webhook-Secret` header.
   - Mode is determined at startup from `WHATSAPP_MODE` environment variable.
2. **Payload Normalization:** Extract `phone_number`, `content`, `content_type`, `timestamp`, `whatsapp_message_id` into `InboundMessageEvent`. The normalization logic adapts to the source schema (Cloud API schema for production, Baileys event schema for dev/testing). Both produce an identical `InboundMessageEvent` — all downstream modules (M2–M9) are unaffected.
3. **Content Type Check:** If `content_type == voice_note` → set `requires_escalation = true` flag.
4. **Rate Limit Check:** Query Redis `ratelimit:{customer_id}:{minute}`. If count > 10 → reject with 429.
5. **Emit Event:** Publish `InboundMessageEvent` to Message Queue (M3).
6. **Outbound Dispatch (Dual-Mode):**
   - **Production mode:** Accept `OutboundMessageDTO` from M4, format into WhatsApp send schema, send via WhatsApp Business API.
   - **Dev/Testing mode:** Accept `OutboundMessageDTO` from M4, send HTTP POST to Baileys bridge API for delivery.

**Dependencies:**
- M3 (Message Queue) — publishes events to
- Redis — rate limiting counters
- WhatsApp Business API — inbound webhooks and outbound dispatch (production mode)
- Baileys Node.js bridge — inbound webhooks and outbound dispatch (dev/testing mode)

**Design Decisions:**
- **Dual-mode architecture:** The gateway supports two WhatsApp transports behind a single `InboundMessageEvent` interface. The active mode is selected via `WHATSAPP_MODE` environment variable (`official` or `baileys`). This enables free development/testing with Baileys and paid production with the official WhatsApp Business API, with zero code changes to modules M2–M9.
- **Baileys bridge isolation:** The Baileys Node.js service runs as a separate Docker container (`whatsapp-bridge`). It manages QR-code authentication, session persistence (`auth_sessions/` volume), and message relay. FastAPI never interacts with WhatsApp Web directly.
- FastAPI handles the WhatsApp Business API transport in production (webhook registration, message send) via async HTTP calls. This decouples the channel adapter from business logic (NFR8: extensibility for Telegram/web).
- Voice note detection happens at gateway level (earliest possible) to trigger immediate escalation (FR9).
- **Production safety:** Baileys mode must NEVER be used with the real MBB business number (ban risk). Baileys is strictly for test phone numbers during development.

**Traceability:** FR1 (message reception), FR9 (voice note escalation trigger), NFR1 (rate limiting for performance)

#### M2: Language Detection Module

**Layer:** Interaction  
**Responsibility:** Detect the dominant language of an inbound message (Lingala, French, or Swahili) and support intra-message code-switching detection.

**Inputs:**
| Input | Source | Format |
|-------|--------|--------|
| Message text content | WhatsApp Gateway (M1) via `InboundMessageEvent` | String (UTF-8) |
| Customer profile (if existing) | Data Layer (PostgreSQL) | `preferred_language` field |

**Outputs:**
| Output | Destination | Format |
|--------|-------------|--------|
| Detected language code | Conversation Engine (M4) | Enum: `lingala`, `french`, `swahili` |
| Confidence score | MAPS Intelligence (M8) | Float 0.0–1.0 |
| Hybrid flag | Conversation Engine (M4) | Boolean |

**Internal Logic:**
1. **Keyword Matching (Fast Path):** Check for high-confidence Lingala markers (`mbote`, `nalingi`, `nazali`, `ezali`, `ndeko`, `tika`, `yaka te`) and Swahili markers (`habari`, `asante`, `karibu`, `nataka`). If ≥2 markers found → set language with confidence 0.9+.
2. **LLM-Assisted Detection (Fallback):** If keyword matching is inconclusive (confidence < 0.6), include a language detection instruction in the Claude prompt: `"Detect dominant language: lingala/french/swahili. Reply in detected language."`.
3. **Sticky Language:** On first message in a conversation, detected language is stored in `conversations.language_detected` and reused for all subsequent messages in that conversation. Only overridden if user explicitly requests a language switch.
4. **Hybrid Detection:** If markers from 2+ languages are present, set `hybrid = true`. Response will mirror the user's mixing style (e.g., Lingala structure with French vocabulary).
5. **Fallback:** If detection fails entirely → default to `french` (FR2 requirement).

**Dependencies:**
- Claude LLM API — fallback language detection
- PostgreSQL — customer language preference lookup

**Design Decisions:**
- Keyword matching first (avoids LLM call for 70%+ of messages where language is obvious) → reduces latency and Claude API cost.
- Language is sticky per conversation, not per message, to avoid jarring language switches mid-flow.

**Traceability:** FR2 (multi-language detection), NFR5 (cultural/linguistic accuracy)

#### M3: Message Queue & Resilience Module

**Layer:** Orchestration  
**Responsibility:** Buffer all inbound messages through a Redis-backed queue to ensure zero message loss during blackouts, manage retry logic, and coordinate message processing order.

**Inputs:**
| Input | Source | Format |
|-------|--------|--------|
| `InboundMessageEvent` | WhatsApp Gateway (M1) | JSON event |
| Relance job triggers | Relance Engine (M6) | Scheduled job ID |
| Recovery signal | System monitor (health check) | Boolean |

**Outputs:**
| Output | Destination | Format |
|--------|-------------|--------|
| Dequeued message for processing | Conversation Engine (M4) | `InboundMessageEvent` |
| Recovery message trigger | WhatsApp Gateway (M1) | `OutboundMessageDTO` |
| Queue health metrics | Analytics Module (M9) | Counters (queue depth, processing rate) |

**Internal Logic:**
1. **Enqueue:** Every `InboundMessageEvent` is pushed to Redis list `queue:messages:pending` (LPUSH). High-priority events (escalations) go to `queue:messages:high_priority`.
2. **Dequeue:** A worker loop continuously RPOPs from `queue:messages:high_priority` first, then `queue:messages:pending`. Processing is handed to Conversation Engine (M4).
3. **Acknowledgment:** Only after successful processing does the message leave the queue. If processing fails, the message is re-queued with an incremented `retry_count`.
4. **Retry Logic:**
   - Max retries: 3
   - Backoff: 5s → 15s → 45s (exponential)
   - After 3 failures → move to dead-letter queue (`queue:messages:dead_letter`) + alert M9.
5. **Blackout Recovery:** When the system detects it was offline (gap in heartbeat), it processes all pending messages in FIFO order and sends recovery message: `"Je suis toujours là même si le courant est coupé 😊"` to each affected customer (FR10).
6. **Persistence:** Redis AOF (Append-Only File) ensures queue survives Redis restart. Snapshots every hour (RDB) as backup.

**Dependencies:**
- Redis — queue storage (AOF-persistent)
- M1 (WhatsApp Gateway) — receives events from, sends recovery messages to
- M4 (Conversation Engine) — dispatches messages to
- M9 (Analytics) — reports queue health

**Design Decisions:**
- Redis List (not Pub/Sub) chosen because messages must persist if consumer is down (blackout scenario).
- Two-priority queue ensures escalations are never blocked behind normal messages.
- Dead-letter queue prevents poison messages from blocking the pipeline.

**Traceability:** FR10 (queue & resilience), NFR2 (reliability), NFR1 (performance — async decoupling)

#### M4: Conversation Engine Module

**Layer:** Business & Intelligence  
**Responsibility:** Manage conversation state, generate AI-powered responses using Claude LLM, apply persuasion principles, and coordinate the conversational flow (qualification → nurturing → conversion).

**Inputs:**
| Input | Source | Format |
|-------|--------|--------|
| Dequeued `InboundMessageEvent` | Message Queue (M3) | JSON event |
| Detected language | Language Detection (M2) | Enum + confidence |
| Session state (cached context) | Redis | Hash (`session:{conversation_id}`) |
| Customer history | PostgreSQL | Customer + Conversation + Lead records |

**Outputs:**
| Output | Destination | Format |
|--------|-------------|--------|
| AI-generated response | WhatsApp Gateway (M1) | `OutboundMessageDTO` |
| Lead qualification trigger | Lead Qualification (M5) | `QualificationRequest` |
| Escalation trigger | Escalation handling (via M3) | `EscalationEvent` |
| MAPS tag data | MAPS Intelligence (M8) | `MAPSTagEvent` |
| Updated session state | Redis | Hash fields |

**Internal Logic:**
1. **Context Loading:** Load session from Redis (`session:{conversation_id}`). If cache miss, load from PostgreSQL `conversations.context` JSONB.
2. **Conversation Stage Routing:**
   - `NEW` → Welcome + first qualification question (delegate to M5).
   - `QUALIFYING` → Continue qualification flow (delegate to M5).
   - `NURTURING` → Product recommendations, pricing, delivery info.
   - `CONVERTING` → Payment options, order confirmation (delegate to M7).
   - `DORMANT` → Handled by Relance Engine (M6).
   - `ESCALATED` → No AI response; Hub Team has control.
3. **LLM Prompt Construction:**
   - System prompt: Master prompt with cultural tone rules ("helpful young Congolese friend"), language instruction, 2–3 sentence limit, emoji guidelines.
   - Context window: Last 5 messages + session state (topic, stage, products discussed).
   - Persuasion instruction: Injected by M5/M7 based on stage (e.g., "Apply reciprocity: offer free tip before asking about intent").
   - Token limit: max 150 tokens per response (enforce short messages).
4. **Response Generation:** Call Claude API with constructed prompt. Timeout: 30s. On timeout → return holding message: `"Un instant, je vérifie ça pour toi… 😊"`.
5. **Opt-Out Detection:** Before responding, check if inbound message contains opt-out signals: `stop`, `arrête`, `non`, `tika`, `yaka te`. If detected → immediately set `customers.opt_out_flag = true`, cancel all pending relances, send confirmation: `"C'est noté. On ne te dérangera plus. Si tu changes d'avis, écris-nous. 😊"`.
6. **Session Update:** Update Redis session with new context (topic, products, stage). Sync to PostgreSQL every 10 minutes or on conversation close.
7. **MAPS Emission:** After every processed message, emit `MAPSTagEvent` to M8 with extracted patterns.

**Dependencies:**
- Claude LLM API — response generation
- Redis — session cache
- PostgreSQL — customer history, conversation persistence
- M2 (Language Detection) — language for prompt
- M5 (Lead Qualification) — qualification flow delegation
- M6 (Relance Engine) — dormant lead handling
- M7 (Conversion & Order) — order flow delegation
- M8 (MAPS Intelligence) — pattern capture
- M1 (WhatsApp Gateway) — outbound dispatch

**Design Decisions:**
- Claude prompt is constructed dynamically (not hardcoded templates) to support hybrid language and contextual persuasion.
- 150-token limit enforced at prompt level ensures 2–3 sentence responses (NFR4).
- Session sync to PostgreSQL every 10 minutes (not per message) reduces DB writes by ~90% while keeping resilience via Redis AOF.

**Traceability:** FR3 (conversation management), FR5 (nurturing), NFR4 (usability), NFR5 (cultural accuracy)

#### M5: Lead Qualification & Nurturing Module

**Layer:** Business & Intelligence  
**Responsibility:** Execute the 2–3 question qualification flow, score leads (Hot/Warm/Cold), manage funnel stage progression, and generate personalized nurturing content.

**Inputs:**
| Input | Source | Format |
|-------|--------|--------|
| Qualification request | Conversation Engine (M4) | `QualificationRequest` (conversation_id, message content) |
| Customer profile | PostgreSQL | Customer record |
| Product catalog data | Configuration / PostgreSQL | Product list with pricing |

**Outputs:**
| Output | Destination | Format |
|--------|-------------|--------|
| Lead score + stage | PostgreSQL (leads table) | `LeadRecord` |
| Next question or nurturing message | Conversation Engine (M4) | String (for LLM prompt injection) |
| Relance scheduling request | Relance Engine (M6) | `RelanceScheduleRequest` |
| MAPS qualification data | MAPS Intelligence (M8) | `MAPSTagEvent` |

**Internal Logic:**
1. **Qualification Flow (2–3 Questions):**
   - Q1: **Location** — `"Tu es à Kinshasa, Lubumbashi ou Goma ?"` (determines delivery zone, pricing, language dialect).
   - Q2: **Product Intent** — `"Tu cherches quel produit ? Câble, powerbank, ou autre chose ?"` (determines product interest).
   - Q3 (conditional): **Usage** — `"C'est pour usage pro ou perso ?"` (only asked if product supports pro/personal distinction; refines score).
2. **Scoring Algorithm:**
   - **HOT** (score ≥ 7): Answered all questions + mentioned price/delivery + active in last 2 hours.
   - **WARM** (score 4–6): Answered 1–2 questions + showed interest but no urgency signals.
   - **COLD** (score ≤ 3): Single message + no follow-up after 24h.
   - Scoring factors: `message_count` (×1), `price_mention` (×2), `delivery_mention` (×2), `time_recency` (×1.5 if < 2h).
3. **Stage Progression:**
   - `AWARENESS` → Customer knows product exists (after Q1).
   - `CONSIDERATION` → Customer comparing options (after Q2, discussing features/price).
   - `DECISION` → Customer ready to buy (asking about payment/delivery method).
   - Progression is **unidirectional** — no regression.
4. **Nurturing Content Generation:**
   - Based on stage + city + product, inject context into Claude prompt:
     - `CONSIDERATION`: `"Mention that the 2m reinforced cable is the most requested by pros in {city}. Include price."`
     - `DECISION`: `"Offer payment options: Orange Money, Airtel Money, M-Pesa, COD. Ask which they prefer."`
   - Embed persuasion hooks (Cialdini):
     - Reciprocity: Free tip relevant to their city/usage.
     - Social proof: `"80% des pros à Gombe choisissent le renforcé."`.
     - Scarcity: Only when genuine (`"Stock limité cette semaine."`).

**Dependencies:**
- M4 (Conversation Engine) — receives requests from, returns prompt instructions to
- M6 (Relance Engine) — schedules relance when lead goes silent
- M8 (MAPS Intelligence) — emits qualification patterns
- PostgreSQL — leads table persistence

**Traceability:** FR4 (lead capture & qualification), FR5 (nurturing), Blueprint (Cialdini, SB7)

#### M6: Relance Engine Module

**Layer:** Business & Intelligence  
**Responsibility:** Manage the strategic re-engagement of silent leads with a strict maximum of 3 value-first relances, respecting blackout hours and opt-out preferences.

**Inputs:**
| Input | Source | Format |
|-------|--------|--------|
| Relance schedule request | Lead Qualification (M5) | `RelanceScheduleRequest` (lead_id, timing) |
| Scheduler tick (hourly cron) | Redis Sorted Set | Due relance IDs |
| Customer opt-out event | Conversation Engine (M4) | `OptOutEvent` |

**Outputs:**
| Output | Destination | Format |
|--------|-------------|--------|
| Relance message to send | WhatsApp Gateway (M1) via Celery task | `OutboundMessageDTO` |
| Relance delivery record | PostgreSQL (relances table) | `RelanceRecord` |
| Relance performance data | MAPS Intelligence (M8) | `MAPSTagEvent` |

**Internal Logic:**
1. **Scheduling:**
   - Relance 1: scheduled_at = last_message_time + 24 hours.
   - Relance 2: scheduled_at = relance_1_delivered_at + 48–72 hours (random jitter to avoid pattern detection).
   - Relance 3: scheduled_at = relance_2_delivered_at + 7–10 days (random jitter).
   - Store in Redis Sorted Set `scheduler:relances` with score = UNIX timestamp.
2. **Execution (Hourly Cron):**
   - `ZRANGEBYSCORE scheduler:relances -inf {now}` → fetch all due relances.
   - For each due relance:
     a. Load lead from PostgreSQL. Check: `opt_out_flag == false` AND `relance_count < 3`.
     b. Check blackout hours: If current time is 22:00–07:00 (Kinshasa timezone, UTC+1) → reschedule to 08:00 next day.
     c. Generate personalized value hook based on attempt number:
        - **Attempt 1:** Value + reminder. Template: `"Hey {name}, j'espère que ça va malgré {city_context}. Voici le prix actualisé pour {product} : {price} FC. 😊"`
        - **Attempt 2:** Social proof + small incentive. Template: `"{testimonial_from_city}. En plus, commande aujourd'hui et gagne {points} points Club ! 🎁"`
        - **Attempt 3:** Loyalty reward + clear opt-out. Template: `"Dernière info : {special_offer}. Si tu ne veux plus recevoir de messages, dis juste 'stop'. On respecte. ✌️"`
     d. Send via M1 (WhatsApp Gateway).
     e. Update PostgreSQL: `relances.delivered_at`, `leads.relance_count += 1`.
     f. Remove from Redis Sorted Set.
3. **Opt-Out Handling:** On `OptOutEvent`, immediately:
   - Cancel all scheduled relances for the customer: `ZREM scheduler:relances {relance_ids}`.
   - Set `customers.opt_out_flag = true`.
   - Delete pending relance records.

**Dependencies:**
- Redis — relance scheduler (Sorted Set)
- PostgreSQL — relance records, lead data, opt-out flags
- M1 (WhatsApp Gateway) — message dispatch
- M4 (Conversation Engine) — opt-out signals
- M8 (MAPS Intelligence) — relance performance capture

**Design Decisions:**
- Random jitter on relance 2 and 3 timing prevents predictable message patterns that feel robotic.
- Blackout hour check uses Kinshasa timezone (UTC+1), not server timezone.
- Relance content is templated (not fully LLM-generated) to ensure compliance with max-3 rule and predictable tone.

**Traceability:** FR7 (relance engine), NFR12 (anti-spam, ethics), Blueprint (Cialdini rhythm)

#### M7: Conversion & Order Module

**Layer:** Business & Intelligence  
**Responsibility:** Handle the in-WhatsApp ordering flow including payment method selection, order creation, payment confirmation tracking, Hub CRM sync, and Club points crediting.

**Inputs:**
| Input | Source | Format |
|-------|--------|--------|
| Conversion trigger | Conversation Engine (M4) | `ConversionRequest` (lead_id, products, payment preference) |
| Payment callback | Mobile Money API (webhook to FastAPI) | Webhook payload |
| Hub CRM order status | Airtable API | Order status update |

**Outputs:**
| Output | Destination | Format |
|--------|-------------|--------|
| Payment instructions message | WhatsApp Gateway (M1) | `OutboundMessageDTO` |
| Order record | PostgreSQL (orders table) | `OrderRecord` |
| Payment record | PostgreSQL (payments table) | `PaymentRecord` |
| Hub CRM order | Airtable API (via Celery task) | JSON |
| Club points credit | Hub CRM | API call |
| Conversion MAPS data | MAPS Intelligence (M8) | `MAPSTagEvent` |

**Internal Logic:**
1. **Payment Method Presentation:**
   - Based on customer city and preference, present options:
     - **Kinshasa:** Orange Money (primary), Airtel Money, bank transfer, COD.
     - **Lubumbashi:** M-Pesa (primary), Airtel Money, COD.
     - **Goma:** M-Pesa (primary), Orange Money, COD.
   - Format: `"Comment tu veux payer ? 1️⃣ Orange Money 2️⃣ Airtel Money 3️⃣ Cash à la livraison"`
2. **Order Creation:**
   - Validate: lead exists, products valid, payment type valid.
   - Create `orders` record (status = `pending`).
   - Create `payments` record (status = `pending`).
   - If `payment_type == mobile_money`: send account details + reference code.
   - If `payment_type == bank_transfer`: send bank account details.
   - If `payment_type == cod`: confirm delivery zone + expected timing.
3. **Payment Confirmation:**
   - Mobile Money callback received → validate HMAC signature → update `payments.status = completed` → update `orders.status = confirmed`.
   - COD: order confirmed on delivery (Hub Team updates via CRM).
   - Bank transfer: manual confirmation by Hub Team or via bank API callback.
4. **Post-Confirmation:**
   - Send confirmation message: `"Commande confirmée ! 🎉 Ref: MBB-{order_id_short}. Livraison en 48h à {zone}. Tu gagnes {points} points Club !"`
   - Sync order to Hub CRM (Airtable) via Celery async task.
   - Credit Club points to customer via Hub CRM API.
   - Update `leads.stage = decision`, `conversations.status = converted`.
5. **Idempotency:** Every order creation uses `X-Idempotency-Key` (Redis cache, TTL 24h) to prevent duplicate orders on retry.

**Dependencies:**
- M1 (WhatsApp Gateway) — payment instructions + confirmation messages
- M4 (Conversation Engine) — conversion trigger
- M8 (MAPS Intelligence) — conversion patterns
- PostgreSQL — orders, payments tables
- Redis — idempotency cache
- Celery — async task execution for CRM sync, payment handling
- Airtable API — order sync, Club points

**Traceability:** FR6 (conversion & order), Blueprint (Hormozi Grand Slam Offer, SB7 Call-to-Action)

#### M8: MAPS Intelligence Module

**Layer:** Business & Intelligence  
**Responsibility:** Capture, tag, store, and aggregate structured intelligence patterns from every interaction in real time to feed the MAPS loop (Analyze → Ideate → Prototype → Scale).

**Inputs:**
| Input | Source | Format |
|-------|--------|--------|
| `MAPSTagEvent` | All business modules (M4, M5, M6, M7) | JSON event |
| Message content (for pattern extraction) | Conversation Engine (M4) | String |
| Lab query requests | Analytics Dashboard (M9) | SQL/API query |

**Outputs:**
| Output | Destination | Format |
|--------|-------------|--------|
| Stored MAPS tags | PostgreSQL (maps_tags table) | `MAPSTagRecord` |
| Aggregated insights | Analytics Dashboard (M9) | JSON (aggregations) |
| Real-time alerts | Lab Team notification (via Celery task) | Alert message |

**Internal Logic:**
1. **Tag Extraction (Per Message):**
   - For every processed message, extract at least 1 tag. Categories:
     - `product_demand`: Product mentioned + context (city, usage type).
     - `silence_reason`: Inferred from conversation drop (blackout, price concern, indecision).
     - `conversion_trigger`: What signal preceded conversion (price confirmation, social proof, scarcity).
     - `language_usage`: Language detected + hybrid patterns + code-switching patterns.
   - Extraction uses keyword matching + Claude LLM context (from M4 response metadata).
2. **Tag Storage:** Insert into `maps_tags` table in real time (no batching — FR8 requirement for immediate availability).
3. **Pattern Aggregation (Daily Batch):**
   - Run daily SQL aggregation: `SELECT pattern, COUNT(*) FROM maps_tags WHERE created_at > NOW() - INTERVAL '1 day' GROUP BY pattern ORDER BY count DESC`.
   - Store results in `lab_insights` materialized view for fast dashboard queries.
4. **Alert Rules:**
   - If a new pattern appears ≥ 10 times in 24h → notify Lab Team via Celery task (Telegram/email).
   - If opt-out rate exceeds 8% in any 7-day window → alert Toronto Supervision.
   - If silence_reason `power_outage` spikes > 2x normal → informational alert.
5. **Tone Audit Support:** Expose endpoint for Lab Team to query random 10% of conversations for weekly tone audit (NFR5).

**Dependencies:**
- PostgreSQL — maps_tags table, lab_insights materialized view
- Celery — alert delivery (Telegram/email)

#### M9: Analytics & Dashboard Module

**Layer:** Observability & Governance  
**Responsibility:** Provide real-time KPI visualization, MAPS insight exploration, funnel metrics, relance performance tracking, and export capabilities via a Streamlit web application.

**Inputs:**
| Input | Source | Format |
|-------|--------|--------|
| Aggregated MAPS data | MAPS Intelligence (M8) / PostgreSQL | SQL queries |
| Funnel metrics | PostgreSQL (leads, orders tables) | SQL queries |
| Relance performance | PostgreSQL (relances table) | SQL queries |
| System health metrics | Prometheus | PromQL queries |

**Outputs:**
| Output | Destination | Format |
|--------|-------------|--------|
| Dashboard web UI | Toronto Supervision, Lab Team | Streamlit app (HTTP) |
| CSV export | User download | CSV file |
| Google Sheets sync | Shared spreadsheet | Sheets API push |

**Internal Logic:**
1. **Dashboard Pages:**
   - **Conversion Funnel:** Leads by stage (awareness → consideration → decision → order) with daily/weekly/monthly filters.
   - **Relance Performance:** Response rate per attempt (target: 35–45% on 1st), opt-out rate (target: <8%), by city and language.
   - **Response Times:** 95th percentile first-response time (target: <60s), average processing time.
   - **Language Distribution:** Breakdown of interactions by language (Lingala/French/Swahili), hybrid rate.
   - **MAPS Insights:** Top 20 patterns by category (product demand, silence reasons, conversion triggers) with trend lines.
   - **System Health:** Queue depth, dead-letter count, error rate, uptime.
2. **Data Refresh:** Dashboard queries PostgreSQL directly (read replica if needed). Refresh interval: 5 minutes for KPIs, 1 hour for MAPS aggregations.
3. **Export:**
   - CSV: Generate from current dashboard view, download via browser.
   - Google Sheets: Push daily summary via Sheets API (scheduled by Celery Beat).
4. **Access Control:** Streamlit app behind Nginx with HTTP Basic Auth. Roles:
   - `admin` (Toronto): Full access.
   - `lab`: MAPS insights + tone audit.
   - `hub`: Funnel + relance performance.

**Dependencies:**
- PostgreSQL — all persistent data queries
- Prometheus — system health metrics
- Celery Beat — Google Sheets export scheduling
- Nginx — reverse proxy + auth

**Traceability:** FR11 (analytics & dashboard), NFR10 (observability)

## 8. Future Integration Architecture (MBB HUB & MBB BOX)

### Overview

MBB ya Kin is designed to integrate with other MBB ecosystem systems using an **Adapter Pattern** to ensure loose coupling and minimal rework. All external system integrations are abstracted behind standardized adapter interfaces so that upstream modules (M2–M9) never call external APIs directly.

### Adapter Pattern (Phase 1.5 Ready)

**Current Adapters (Phase 1):**
- ✅ **WhatsAppAdapter** (M1) — messaging channel (dual-mode: Baileys bridge / Official API)
- ✅ **AirtableAdapter** (M7) — order sync, Club points, customer CRM via Celery tasks
- ✅ **ClaudeAdapter** (M4) — LLM provider for AI response generation
- ✅ **MobileMoneyAdapter** (M7) — payment processor (Orange Money, Airtel Money, M-Pesa)

**Future Adapters (Planned):**
- 🔮 **MBBHubAdapter** (Phase 2) — Hub CRM integration (replaces AirtableAdapter)
- 🔮 **MBBBoxAdapter** (Phase 2+) — Inventory and product catalog sync
- Other adapters will be specified in the future if needed (e.g., logistics partners, analytics platforms)

### Design Principle: Zero Code Changes

When a new integration is needed:
1. **Create** a new adapter class implementing the standard interface (e.g., `CRMAdapterInterface` or `InventoryAdapterInterface`).
2. **Register** the adapter in the configuration (environment variable or config file).
3. **Existing modules (M2–M9) remain completely untouched** — they call the adapter interface, not the concrete implementation.

```
┌───────────────────────────────────────────────────────────────────┐
│  MODULE M7 (Conversion & Order)                                    │
│  calls: crm_adapter.sync_order(order)                             │
│  calls: inventory_adapter.check_stock(product_id, city)           │
└───────────────┬───────────────────────────┬───────────────────────┘
                │                           │
       ┌────────▼────────┐        ┌────────▼────────┐
       │  CRMAdapter     │        │ InventoryAdapter │
       │  Interface       │        │  Interface        │
       └────────┬────────┘        └────────┬────────┘
        ┌───────┼───────┐          ┌───────┼───────┐
        ▼               ▼          ▼               ▼
 ┌──────────────┐ ┌──────────┐ ┌──────────────┐ ┌──────────────┐
 │ Airtable     │ │ MBB HUB  │ │ Static       │ │ MBB BOX      │
 │ Adapter      │ │ Adapter  │ │ Catalog      │ │ Adapter      │
 │ (Phase 1)    │ │ (Phase 2)│ │ (Phase 1)    │ │ (Phase 2+)   │

```

### MBBHubAdapter (Phase 2)

**Purpose:** Replace AirtableAdapter as the primary CRM backend for customer data, order routing, Club loyalty, and escalation handoff.

**Interface Methods:**

| Method | Description | Current (Airtable) | Future (MBB HUB) |
|--------|-------------|-------------------|--------------------|
| `sync_lead(lead)` | Push qualified lead to CRM | Airtable record create | HUB API POST |
| `sync_order(order)` | Push order + items to CRM | Airtable record create | HUB API POST |
| `credit_club_points(customer_id, points)` | Add loyalty points | Airtable field update | HUB API PUT |
| `get_customer_profile(phone)` | Retrieve customer CRM data | Airtable record GET | HUB API GET |
| `create_escalation(ticket)` | Send escalation to Hub Team queue | Airtable + Telegram | HUB built-in queue |

**Configuration:**
```env
CRM_ADAPTER=airtable          # Phase 1
CRM_ADAPTER=mbb_hub           # Phase 2 (switch by changing this value)
MBB_HUB_API_URL=https://hub.mbb.cd/api/v1
MBB_HUB_API_KEY=<hub_api_key>  # Stored as Docker secret
```

**Transition Plan:**
1. Both adapters coexist during Phase 1.5 transition.
2. `CRM_ADAPTER` env variable selects the active adapter.
3. Dual-write mode available: write to both Airtable AND MBB HUB for validation.
4. Once verified, switch to MBB HUB only.

### MBBBoxAdapter (Phase 2+)

**Purpose:** Provide real-time product inventory, stock levels, dynamic pricing, and catalog data for nurturing (M5) and conversion (M7) flows.

**Interface Methods:**

| Method | Description | Current (Static) | Future (MBB BOX) |
|--------|-------------|------------------|-------------------|
| `check_stock(product_id, city)` | Get stock availability | Static config file | BOX API GET |
| `get_price(product_id, city)` | Get current price | Static config file | BOX API GET |
| `get_catalog(city)` | List available products | Static config file | BOX API GET |
| `reserve_stock(product_id, qty)` | Reserve items for order | Not available | BOX API POST |

**Configuration:**
```env
INVENTORY_ADAPTER=static       # Phase 1 (static JSON catalog)
INVENTORY_ADAPTER=mbb_box      # Phase 2+ (switch by changing this value)
MBB_BOX_API_URL=https://box.mbb.cd/api/v1
MBB_BOX_API_KEY=<box_api_key>  # Stored as Docker secret
```

**Graceful Fallback:**
- If MBB BOX is unreachable (timeout, error), the system falls back to the static catalog automatically.
- Circuit breaker pattern (5 failures in 60s → OPEN → 30s recovery) protects against cascade failures.
- MAPS tag emitted: `category = 'silence_reason'`, `pattern = 'box_api_unreachable'`.
