# 4. Security Design

## Purpose

This document defines the security architecture for the MBB ya Kin system across 5 layers: transport, API gateway, application, data, and infrastructure. It specifies authentication mechanisms (JWT for internal services, HMAC for webhooks, HTTP Basic for dashboards), authorization rules (role-permission matrix), encryption (TLS 1.3, bcrypt, LUKS), rate limiting, and compliance controls for DRC data protection regulations.

## Audience

- **Security Engineers**: Validate threat model and defense-in-depth design
- **DevOps/Infrastructure Teams**: Deploy TLS, LUKS encryption, firewall rules, Docker security
- **Backend Developers**: Implement JWT validation, HMAC verification, input sanitization
- **Compliance Officers**: Review data protection and privacy controls

---

### 4.1 Security Architecture Overview

Security is designed in layers (defense-in-depth) aligned with the system's layered architecture. Each layer has independent security controls so that a breach at one layer does not compromise the entire system.

```
┌──────────────────────────────────────────────────────────────────────┐
│  LAYER 1: TRANSPORT SECURITY   (TLS 1.3 + Nginx)                     │
├──────────────────────────────────────────────────────────────────────┤
│  LAYER 2: API GATEWAY SECURITY (Rate Limiting + Auth)                │
├──────────────────────────────────────────────────────────────────────┤
│  LAYER 3: APPLICATION SECURITY (Input Validation + Business Rules)   │
├──────────────────────────────────────────────────────────────────────┤
│  LAYER 4: DATA SECURITY        (Encryption + Masking + Minimal Data) │
├──────────────────────────────────────────────────────────────────────┤
│  LAYER 5: INFRASTRUCTURE       (Firewall + Docker Isolation)         │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.2 Authentication Mechanisms

#### 4.2.1 Internal Service Authentication (Celery Workers → FastAPI)

**Method:** JWT (JSON Web Token) with HS256 signing.

| Parameter | Value |
|-----------|-------|
| Algorithm | HS256 |
| Secret length | 256-bit (32 bytes), generated via `openssl rand -hex 32` |
| Token lifetime | 24 hours |
| Issuer claim | `celery-mbb` |
| Subject claim | `celery-service-account` |
| Role claim | `orchestrator` |

**JWT Payload Structure:**

```json
{
  "iss": "celery-mbb",
  "sub": "celery-service-account",
  "role": "orchestrator",
  "iat": 1713106800,
  "exp": 1713193200
}
```

**Token Refresh:** Celery worker generates a new token every 12 hours (before expiration) using the shared secret stored in Docker environment variable `MBB_JWT_SECRET`.

**Validation Flow (FastAPI middleware):**
1. Extract `Authorization: Bearer {token}` header.
2. Decode and verify signature using `MBB_JWT_SECRET`.
3. Check `exp` claim (reject if expired).
3. Check `role` claim (must be `orchestrator` for Celery workers, `dashboard` for Streamlit).
5. On failure → return 401 with generic message (no leak of validation details).

**Key Storage:**
- `MBB_JWT_SECRET` stored as Docker secret (not in code, not in `.env` file committed to VCS).
- Rotated quarterly. On rotation: issue new token to Celery workers, old tokens rejected immediately.

---

#### 4.2.2 Webhook Authentication (Mobile Money → FastAPI)

**Method:** HMAC-SHA256 signature verification.

| Parameter | Value |
|-----------|-------|
| Algorithm | HMAC-SHA256 |
| Secret | Per-provider shared secret (Orange, Airtel, M-Pesa) |
| Header | `X-Signature: sha256={hex_digest}` |

**Verification Steps:**
1. Read raw request body (bytes, not parsed JSON).
2. Compute `HMAC-SHA256(body, provider_secret)`.
3. Compare with `X-Signature` header value using `hmac.compare_digest()` (constant-time comparison to prevent timing attacks).
4. On mismatch → return 401. Log the attempt with source IP.

**Secret Storage:** Each provider has a dedicated Docker secret:
- `MBB_ORANGE_MONEY_SECRET`
- `MBB_AIRTEL_MONEY_SECRET`
- `MBB_MPESA_SECRET`

---

#### 4.2.4 MBB HUB & MBB BOX Authentication (Phase 2 / Phase 2+)

**Method:** API Key authentication with TLS 1.3 transport.

| Parameter | MBB HUB (Phase 2) | MBB BOX (Phase 2+) |
|-----------|-------------------|---------------------|
| Auth method | API Key in `Authorization: Bearer {key}` header | API Key in `Authorization: Bearer {key}` header |
| Transport | HTTPS (TLS 1.3) | HTTPS (TLS 1.3) |
| Secret storage | Docker secret `MBB_HUB_API_KEY` | Docker secret `MBB_BOX_API_KEY` |
| Rotation | Quarterly | Quarterly |
| Fallback on auth failure | Retry 3x, then fallback to Airtable (HUB) or static catalog (BOX) | Same |

**Adapter-Level Security:**
- MBBHubAdapter and MBBBoxAdapter each manage their own authentication headers.
- API keys are never logged, never included in error responses, and never stored in `.env` files committed to VCS.
- If MBB HUB or BOX returns 401/403, the adapter logs the event, alerts ops, and falls back gracefully (Airtable or static catalog) without disrupting customer conversations.

---

#### 4.2.3 Dashboard Authentication (Streamlit)

**Method:** HTTP Basic Auth via Nginx reverse proxy.

| Parameter | Value |
|-----------|-------|
| Auth type | HTTP Basic (over HTTPS) |
| Password storage | `htpasswd` file with bcrypt hashing |
| Roles | `admin`, `lab`, `hub` |

**Role-Based Access (Analytics + Admin Operations):**

| Role | Analytics Pages | Admin Operations Pages | Assigned To |
|------|----------------|----------------------|-------------|
| `admin` | All pages (funnel, relance, MAPS, system health, exports) | Bot Configuration, Escalation Manager, Content Manager, System Control, Audit Log | Toronto Supervision |
| `lab` | MAPS insights, language distribution | Tone Audit Console, MAPS Tag Manager | Lab Team |
| `hub` | Funnel, relance performance | Lead Operations (status override), Escalation Response | Hub Team |

> **Design Decision:** The Streamlit dashboard serves as a unified command center — combining read-only analytics with role-gated write operations. Admin write operations are routed through FastAPI endpoints (not direct DB writes from Streamlit), maintaining the same API security layer used by all other services. Every write operation is logged in the `admin_audit_log` table for traceability.

**Nginx Configuration:**

```nginx
location /dashboard/ {
    auth_basic "MBB Dashboard";
    auth_basic_user_file /etc/nginx/.htpasswd;
    proxy_pass http://streamlit:8501;
}
```

**Password file management:** Passwords generated using `htpasswd -nbBC 12 {username} {password}`. Bcrypt cost factor 12.

Streamlit never writes directly to the database.

#### 4.3.2 Authorization Enforcement

Authorization is enforced at two levels:

1. **FastAPI Middleware (Application Level):**
   - JWT `role` claim checked against endpoint permission map.
   - Unauthorized requests return 403 (Forbidden).

2. **Nginx (Transport Level):**
   - Payment webhook endpoint (`/api/v1/payments/*/callback`) only accessible from whitelisted IPs (Mobile Money provider IP ranges).
   - Dashboard (`/dashboard/*`) requires HTTP Basic Auth.
   - All other `/api/v1/*` endpoints only accessible from internal Docker network + Celery worker container IP.

### 4.4 Data Protection

#### 4.4.1 Data at Rest

| Data Store | Encryption | Mechanism |
|------------|------------|-----------|
| PostgreSQL | Volume-level encryption | LUKS (dm-crypt) on VPS disk |
| Redis | AOF file on encrypted volume | Same LUKS volume |
| Backups | Encrypted before upload | `gpg --symmetric --cipher-algo AES256` |
| Docker secrets | Encrypted in Docker secret store | Docker built-in |
| Environment variables | `.env` file with restricted permissions | `chmod 600 .env`, not in Git |

#### 4.4.2 Data in Transit

| Path | Encryption | Details |
|------|------------|---------|
| Customer ↔ WhatsApp | End-to-end (WhatsApp) | WhatsApp E2E encryption |
| WhatsApp API ↔ FastAPI (production) | TLS 1.3 | HTTPS webhook |
| Baileys bridge ↔ WhatsApp (dev/testing) | WhatsApp Web protocol | Modified WebSocket (Baileys library); dev/testing only with test phone number |
| Baileys bridge ↔ FastAPI (dev/testing) | TLS 1.3 (internal) | HTTP POST within Docker network; webhook secret header validation |
| Celery Workers ↔ FastAPI | Internal | Celery uses Redis broker (internal Docker network only) |
| FastAPI ↔ Claude API | TLS 1.3 | HTTPS API calls |
| FastAPI ↔ PostgreSQL | TLS (pg_ssl) | `sslmode=require` in connection string |
| FastAPI ↔ Redis | Unencrypted (internal only) | Redis on localhost/Docker internal network only |
| FastAPI ↔ MBB HUB API (Phase 2) | TLS 1.3 | HTTPS API calls via MBBHubAdapter |
| FastAPI ↔ MBB BOX API (Phase 2+) | TLS 1.3 | HTTPS API calls via MBBBoxAdapter |
| Browser ↔ Dashboard | TLS 1.3 | HTTPS via Nginx |

**Redis unencrypted justification:** Redis is only accessible within the Docker network (`redis` service, no port forwarding to host). Network-level isolation provides sufficient protection. Adding TLS to Redis would add latency to the <60s response target.

#### 4.4.3 Sensitive Data Handling

| Data | Classification | Storage | Display | Logging |
|------|---------------|---------|---------|---------|
| Phone number | PII | Full (`+243987654321`) | Masked (`+243******321`) in dashboard/logs | Masked |
| Customer name | PII | Full | Full (Hub Team only) | Redacted |
| Message content | PII | Full (for MAPS) | Full (Hub Team escalation only) | First 50 chars only |
| Payment details | Financial | Encrypted volume | Masked account numbers | Transaction ID only |
| Conversation context | Internal | JSONB (full) | Hub Team only | Not logged |
| Claude API key | Secret | Docker secret | Never displayed | Never logged |
| JWT secret | Secret | Docker secret | Never displayed | Never logged |
| HMAC secrets | Secret | Docker secrets | Never displayed | Never logged |

#### 4.4.4 Password & Secret Hashing

| Secret Type | Algorithm | Parameters |
|-------------|-----------|------------|
| Dashboard passwords | bcrypt | Cost factor 12 |
| API keys (if stored) | SHA-256 (hash for comparison) | With salt |

**No user passwords exist in this system** — customers authenticate via WhatsApp identity (phone number). Dashboard users use HTTP Basic Auth (bcrypt-hashed passwords in `htpasswd`).

### 4.5 API Security Controls

#### 4.5.1 Input Validation (OWASP Protection)

| OWASP Risk | Mitigation | Implementation |
|------------|------------|----------------|
| **Injection (SQL)** | Parameterized queries only | SQLAlchemy ORM with bound parameters, never raw string interpolation |
| **Injection (NoSQL/JSONB)** | JSONB values validated via Pydantic | No raw JSONB construction from user input |
| **XSS** | Not applicable (API-only, no HTML rendering) | JSON responses only, `Content-Type: application/json` |
| **Broken Authentication** | JWT + HMAC with constant-time comparison | `hmac.compare_digest()`, no custom auth logic |
| **Sensitive Data Exposure** | Response filtering, PII masking | DTOs exclude internal fields (see Section 3.4) |
| **Broken Access Control** | Role-based authorization per endpoint | JWT role claim + Nginx IP restrictions |
| **Security Misconfiguration** | Hardened Nginx, Docker security defaults | Security headers (see below) |
| **Mass Assignment** | Pydantic models define allowed fields only | Extra fields rejected (`model_config = {"extra": "forbid"}`) |
| **SSRF** | No user-controlled URLs in server requests | Claude API URL and webhook URLs are hardcoded in config |

#### 4.5.2 Security Headers (Nginx)

```nginx
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header X-XSS-Protection "0" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Content-Security-Policy "default-src 'none'; frame-ancestors 'none'" always;
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
```

#### 4.5.3 Rate Limiting (DDoS Mitigation)

| Scope | Limit | Window | Enforcement |
|-------|-------|--------|-------------|
| Per customer phone | 10 messages | 1 minute | Redis counter + TTL |
| Per internal service IP | 1,000 requests | 1 minute | Nginx `limit_req` |
| Per webhook IP | 100 requests | 1 minute | Nginx `limit_req` |
| Global | 10,000 requests | 1 minute | Nginx `limit_req` |

**Nginx Rate Limiting:**

```nginx
limit_req_zone $binary_remote_addr zone=api:10m rate=100r/m;
limit_req_zone $binary_remote_addr zone=webhook:10m rate=100r/m;

location /api/v1/ {
    limit_req zone=api burst=20 nodelay;
}

location /api/v1/payments/ {
    limit_req zone=webhook burst=10 nodelay;
}
```

#### 4.5.4 Replay Attack Prevention

**Payment Webhooks:**
1. `transaction_id` stored in Redis on first processing (TTL: 7 days).
2. On duplicate `transaction_id` → return 409 Conflict, do not re-process.
3. Timestamp validation: reject callbacks with `timestamp` > 5 minutes old.

**Message Deduplication:**
1. `whatsapp_message_id` stored in Redis on first processing (TTL: 24 hours).
2. On duplicate → return 200 with cached response (idempotent).

### 4.6 Infrastructure Security

#### 4.6.1 Firewall (UFW)

```bash
# Default deny incoming
ufw default deny incoming
ufw default allow outgoing

# Allow SSH (restricted to admin IP)
ufw allow from {ADMIN_IP} to any port 22

# Allow HTTP/HTTPS (public)
ufw allow 80/tcp
ufw allow 443/tcp

# Deny all other ports
ufw enable
```

## Deployment Security Checklist

- [ ] TLS certificates installed (must be valid, not self-signed in production)
- [ ] Nginx configured with TLS 1.3 only (TLS 1.2 disabled)
- [ ] Docker secrets created for `MBB_JWT_SECRET`, provider HMAC secrets
- [ ] LUKS encryption enabled on volume containers
- [ ] Firewall rules: FastAPI, Celery (internal only); PostgreSQL, Redis (internal only); Nginx (0.0.0.0:80/443)
- [ ] Credentials rotated: JWT secret quarterly, HMAC secrets semi-annually
- [ ] Rate limiting configured: 10 msgs/min per customer
- [ ] Audit logging enabled for all auth events (login, token issue, permission denial)

#### 4.6.3 Backup Security

| Backup Type | Frequency | Encryption | Retention |
|-------------|-----------|------------|-----------|
| PostgreSQL full dump | Every 6 hours | AES-256 (gpg) | 30 days |
| PostgreSQL WAL archive | Continuous | AES-256 (gpg) | 7 days |
| Redis RDB snapshot | Every 1 hour | Volume encryption | 7 days |
| Configuration files | On change | AES-256 (gpg) | 90 days |

**Backup flow:**
1. `pg_dump` creates SQL dump.
2. `gpg --symmetric --cipher-algo AES256 --passphrase-file /run/secrets/backup_key dump.sql` encrypts.
3. Upload to off-site storage (separate VPS or cloud bucket).
4. Verify restore capability monthly.

### 4.7 Privacy & Consent Controls

#### 4.7.1 Consent Flow

1. **First Message:** Bot sends consent request: `"Salut ! Pour mieux t'aider, on garde quelques infos (nom, ville, historique). Tu acceptes ? Dis 'oui' pour continuer. 😊"`
2. **On "oui":** Set `customers.consent_given = true`, `customers.consent_timestamp = NOW()`.
3. **On "non" or silence:** Bot still responds to messages but does NOT:
   - Store conversation history beyond current session.
   - Create lead records.
   - Schedule relances.
   - Generate MAPS tags.
4. **Data Deletion:** At any time, customer can request deletion (EP-22). All PII removed within 1 hour.

#### 4.7.2 Data Minimization

| Data | Stored | Justification | Retention |
|------|--------|---------------|-----------|
| Phone number | Yes | Primary identity (WhatsApp) | Until deletion request |
| Name | Yes (optional) | Personalized experience | Until deletion request |
| City | Yes | Delivery zone + pricing | Until deletion request |
| Message content | Yes | MAPS intelligence + escalation context | 90 days |
| Conversation context | Yes | Session continuity | Active session + 30 days |
| Payment transaction ID | Yes | Financial audit | 365 days (anonymized) |
| IP addresses | No | Not needed (WhatsApp proxy) | Never stored |
| Device info | No | Not needed | Never stored |
