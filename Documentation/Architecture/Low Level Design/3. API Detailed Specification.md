# 3. API Detailed Specification

## Purpose

This document specifies the complete FastAPI REST interface (25 core endpoints + 8 admin operations endpoints + planned Phase 2/2+ endpoints) that the system uses to process WhatsApp messages, orchestrate the MBB ya Kin business logic, and provide admin operations via the Streamlit dashboard. It includes request/response schemas, validation rules, error codes, authentication methods, and DTOs. This is the contract between the application layer (FastAPI), async task layer (Celery), dashboard (Streamlit), and external consumers.

## Audience

- **Celery Task Developers**: Integrate these endpoints into async task workflows
- **Backend Developers**: Implement these endpoints with FastAPI and Pydantic models
- **API Consumers**: Use these specifications for third-party integrations
- **QA/Testing**: Validate endpoints against these specifications

---

### 3.1 API Design Principles

**Base URL:** `https://api.mbb.cd/api/v1`  
**Content Type:** `application/json` (all requests and responses)  
**Authentication:** JWT Bearer token (internal service auth), HMAC-SHA256 (Mobile Money webhooks)  
**Versioning:** URL path prefix (`/api/v1/`). Breaking changes → `/api/v2/`.  
**Compression:** gzip for responses > 1 KB (DRC 3G bandwidth optimization).  
**Idempotency:** All POST/PUT endpoints accept optional `X-Idempotency-Key` header (UUID).

**Standard Request Headers:**

| Header | Required | Description |
|--------|----------|-------------|
| `Content-Type` | Yes | `application/json` |
| `Authorization` | Yes | `Bearer {jwt_token}` |
| `X-Idempotency-Key` | Recommended (POST/PUT) | UUID for retry safety |
| `X-Request-ID` | Optional | Request tracing (auto-generated if missing) |
| `Accept-Encoding` | Optional | `gzip` |

**Standard Response Headers:**

| Header | Description |
|--------|-------------|
| `Content-Type` | `application/json; charset=utf-8` |
| `X-Request-ID` | Echoed or generated request trace ID |
| `X-Response-Time` | Processing time in ms |
| `X-RateLimit-Limit` | Max requests per window |
| `X-RateLimit-Remaining` | Remaining requests in window |

#### EP-01: POST `/api/v1/messages`

**Purpose:** Process inbound WhatsApp message (called by WhatsApp Business API webhook or Baileys bridge).  
**Module:** M1 (Gateway) → M3 (Queue) → M4 (Conversation Engine)  
**Auth:** JWT Bearer  

**Request Body:**

| Field | Type | Required | Validation | Description |
|-------|------|----------|------------|-------------|
| `message_id` | UUID | Yes | Valid UUID v4 | Unique message identifier |
| `customer_phone` | string | Yes | Regex: `^\+243[0-9]{9}$` | DRC E.164 phone number |
| `content` | string | Yes | Max 4096 chars, non-empty | Message text body |
| `content_type` | enum | Yes | `text`, `voice_note`, `image` | Message media type |
| `timestamp` | ISO 8601 | Yes | Not in future (>5 min tolerance) | Message timestamp |
| `whatsapp_message_id` | string | Yes | Max 100 chars | WhatsApp external msg ID |

**Response (200 OK — processed):**

```json
{
  "status": "processed",
  "conversation_id": "uuid",
  "response": {
    "content": "Mbote! Ezali kitoko ete ozali ko-luka câble ya 2m...",
    "language": "lingala",
    "processing_time_ms": 1234
  },
  "lead": {
    "lead_id": "uuid",
    "score": "warm",
    "stage": "consideration"
  },
  "maps_tags_created": 2
}
```

**Response (202 Accepted — queued during degraded mode):**

```json
{
  "status": "queued",
  "queue_position": 5,
  "estimated_processing_seconds": 30
}
```

**Status Codes:**

| Code | Condition |
|------|-----------|
| 200 | Message processed, response generated |
| 202 | Message queued (system under load or recovering) |
| 400 | Invalid payload (validation failure) |
| 401 | Invalid or missing JWT |
| 429 | Rate limit exceeded (>10 msgs/min from same customer) |
| 500 | Internal server error |
| 502 | Claude LLM API unreachable |

**Validation Rules:**
1. Phone number must be valid DRC E.164 format.
2. Content must not be empty or exceed WhatsApp limit (4096 chars).
3. Timestamp must not be more than 5 minutes in the future (clock skew tolerance).
4. `whatsapp_message_id` must be unique (idempotency — reject duplicate delivery).
5. If `content_type = voice_note`, immediately flag for escalation (no AI processing of audio).

**Processing Flow:**
1. Validate JWT (production mode) or webhook secret (Baileys dev/testing mode) → Validate payload → Check rate limit (Redis).
2. Check `whatsapp_message_id` dedup (Redis, TTL 24h).
3. Load/create customer → Load/create conversation.
4. Detect language (M2).
5. Check opt-out signals in content.
6. If `content_type == voice_note` → create escalation ticket → return acknowledgment message.
7. Load session from Redis → Construct Claude prompt → Call Claude API (timeout 30s).
8. Save inbound + outbound messages to PostgreSQL.
9. Generate MAPS tags (M8).
10. Update session cache (Redis).
11. Return response to WhatsApp API (production) or Baileys bridge (dev/testing).

#### EP-13: PUT `/api/v1/orders/{order_id}/status`

**Purpose:** Update order status (state machine transitions).  
**Module:** M7  
**Auth:** JWT Bearer  

**Request Body:**

```json
{
  "status": "confirmed",
  "reason": "Payment confirmed via Orange Money"
}
```

**Validation:** Status transitions must follow state machine:
- `pending → confirmed` (on payment)
- `confirmed → preparing` (Hub starts fulfillment)
- `preparing → delivering` (moto dispatched)
- `delivering → delivered` (customer received)
- Any state (except `delivered`) → `cancelled` (with reason)

Invalid transitions return 400.

**Response (200 OK):**

```json
{
  "order_id": "uuid",
  "status": "confirmed",
  "previous_status": "pending",
  "updated_at": "2026-04-14T15:05:00Z"
}
```

**Status Codes:** 200, 400 (invalid transition), 401, 404, 500

#### EP-14: POST `/api/v1/payments/{order_id}/callback`

**Purpose:** Receive payment confirmation from Mobile Money provider (webhook endpoint).  
**Module:** M7  
**Auth:** HMAC-SHA256 signature (header `X-Signature`)  

**Request Body (provider sends):**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `transaction_id` | string | Yes | Provider's unique transaction reference |
| `status` | enum | Yes | `completed`, `failed` |
| `amount` | number | Yes | Amount paid |
| `currency` | string | Yes | `CDF` |
| `timestamp` | ISO 8601 | Yes | Transaction timestamp |
| `failure_reason` | string | No | Reason if status = failed |

**Validation Rules:**
1. Verify HMAC-SHA256 signature from `X-Signature` header using shared secret.
2. `amount` must match `orders.total_amount` (tolerance: ±0).
3. `transaction_id` must not be already processed (prevent replay attacks).

**Response (200 OK):**

```json
{
  "payment_id": "uuid",
  "order_id": "uuid",
  "status": "completed",
  "order_status": "confirmed",
  "club_points_credited": 50
}
```

**Side Effects:**

#### EP-A13: PUT `/api/v1/conversations/{conversation_id}/handoff`

**Purpose:** Manual handoff toggle — allows admin or hub team to instantly switch a conversation between bot control and human control from the Streamlit dashboard.  
**Module:** M9, M4  
**Auth:** HTTP Basic Auth (forwarded by Nginx) — roles: `admin`, `hub`

**Request Body:**

```json
{
  "target_mode": "human",
  "assigned_to": "Marie Nkulu",
  "reason": "Customer requesting specific technical info about cable installation"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `target_mode` | string | Yes | `"human"` (take over) or `"bot"` (return to bot) |
| `assigned_to` | string | Conditional | Required when `target_mode = "human"` — Hub Team member name |
| `reason` | string | Yes | Justification for the manual handoff |

**Side Effects (target_mode = "human" — Take Over):**
1. Update `conversations.status` from `active` → `escalated`.
2. Create an `escalation_ticket` with `reason = 'manual_handoff'`, `priority = 'medium'`, `assigned_to` from request.
3. Bot stops responding to this conversation (M4 checks `conversations.status` before generating responses).
4. Insert `admin_audit_log` entry: `action = 'manual_handoff_to_human'`.
5. Emit MAPS tag: `category = 'silence_reason'`, `pattern = 'manual_handoff'`.

**Side Effects (target_mode = "bot" — Return to Bot):**
1. Update `conversations.status` from `escalated` → `active`.
2. Resolve the associated `escalation_ticket` with `resolution_notes = reason`.
3. Bot resumes responding to this conversation.
4. Insert `admin_audit_log` entry: `action = 'manual_handoff_to_bot'`.
5. Optionally send a recovery message to the customer: "Merci pour ta patience, je suis de retour 😊" (language-adapted).

**Response (200 OK):**

```json
{
  "conversation_id": "uuid",
  "previous_mode": "bot",
  "current_mode": "human",
  "escalation_ticket_id": "uuid",
  "assigned_to": "Marie Nkulu",
  "timestamp": "2026-04-14T15:30:00Z"
}
```

**Error Responses:**
- 400: Invalid `target_mode`, missing required fields, conversation already in target mode.
- 401: Unauthorized (missing or invalid credentials).
- 403: Role not authorized (only `admin` and `hub` can perform handoff).
- 404: Conversation not found.
- 500: Internal server error.

**Validation Rules:**
- Cannot switch to `"human"` if conversation is already `escalated`.
- Cannot switch to `"bot"` if conversation is already `active`.
- `assigned_to` must match a known Hub Team member (validated against config).

### 3.4 Pydantic Data Transfer Objects (DTOs)

All request/response bodies are validated via Pydantic models in FastAPI. Key DTOs:

**Inbound Message DTO:**

```python
class InboundMessageDTO(BaseModel):
    message_id: UUID
    customer_phone: str = Field(..., pattern=r'^\+243[0-9]{9}$')
    content: str = Field(..., min_length=1, max_length=4096)
    content_type: Literal['text', 'voice_note', 'image']
    timestamp: datetime
    whatsapp_message_id: str = Field(..., max_length=100)
```

**Lead Create DTO:**

```python
class CreateLeadDTO(BaseModel):
    conversation_id: UUID
    score: Literal['hot', 'warm', 'cold']
    score_value: int = Field(..., ge=0, le=10)
    stage: Literal['awareness', 'consideration', 'decision'] = 'awareness'
    intent: Literal['product_inquiry', 'support', 'club_loyalty']
    product_interest: list[str] = Field(..., min_length=1, max_length=10)
    source: str = Field(..., max_length=50)
```

**Order Create DTO:**

```python
class OrderItemDTO(BaseModel):
    product_id: str = Field(..., max_length=50)
    quantity: int = Field(..., ge=1)
    unit_price: int = Field(..., gt=0)  # Congolese Francs

class CreateOrderDTO(BaseModel):

    payment_type: Literal['mobile_money', 'bank_transfer', 'cod']
```

**Relance Schedule DTO:**

```python
class ScheduleRelanceDTO(BaseModel):
    lead_id: UUID
    attempt_number: int = Field(..., ge=1, le=3)
    scheduled_at: datetime
    value_hook: str = Field(..., max_length=500)
    hook_type: Literal['reciprocity', 'social_proof', 'scarcity', 'loyalty']

    @field_validator('scheduled_at')
    @classmethod
    def validate_not_in_blackout(cls, v):
        kinshasa_hour = v.astimezone(ZoneInfo('Africa/Kinshasa')).hour
        if kinshasa_hour >= 22 or kinshasa_hour < 7:
            raise ValueError('Cannot schedule relance during blackout hours (22:00-07:00 Kinshasa)')
        return v
```
