# 2. Database Design

## Purpose

This document defines the data persistence layer for the MBB ya Kin system. It specifies the PostgreSQL schema (9 tables), Redis structures (6 cache types), materialized views for analytics, indexing strategy, and data integrity constraints. All designs account for DRC locale requirements (UTF-8 encoding for Lingala/Swahili, UTC+1 timezone, French collation).

## Audience

- **Backend Developers**: Implement migrations and database initialization according to these specifications
- **DBAs/DevOps**: Deploy PostgreSQL 16 and Redis with correct configuration
- **Data Engineers**: Use materialized views and indexes for analytics queries
- **Security Teams**: Verify encryption, masking, and audit requirements

---

### 2.1 Physical Database Architecture

**RDBMS:** PostgreSQL 16  
**Encoding:** UTF-8 (full Unicode — required for Lingala/Swahili characters and emoji)  
**Collation:** `fr_CD.UTF-8` (French — DRC locale) with ICU collation fallback  
**Timezone:** All timestamps stored as `TIMESTAMPTZ` (UTC). Application converts to `Africa/Kinshasa` (UTC+1) for display and blackout-hour logic.

**Schema Name:** `mbb` (all tables under `mbb` schema to isolate from default `public`)

```sql
CREATE SCHEMA IF NOT EXISTS mbb;
SET search_path TO mbb, public;
```

#### Table: `mbb.customers`

**Purpose:** Store unique WhatsApp user profiles. Primary identity anchor for the entire system.

| Column | Data Type | Constraints | Description |
|--------|-----------|-------------|-------------|
| `phone_number` | `VARCHAR(20)` | `PRIMARY KEY` | E.164 format: `+243XXXXXXXXX` |
| `name` | `VARCHAR(100)` | `NULL` | Customer name (collected during conversation) |
| `city` | `VARCHAR(50)` | `NOT NULL` | Kinshasa, Lubumbashi, Goma |
| `preferred_language` | `VARCHAR(10)` | `NOT NULL DEFAULT 'french'` | lingala, french, swahili |
| `opt_out_flag` | `BOOLEAN` | `NOT NULL DEFAULT FALSE` | If TRUE, all relances blocked system-wide |
| `opt_out_at` | `TIMESTAMPTZ` | `NULL` | Timestamp of opt-out for compliance audit |
| `consent_given` | `BOOLEAN` | `NOT NULL DEFAULT FALSE` | Explicit consent for data processing |
| `consent_timestamp` | `TIMESTAMPTZ` | `NULL` | When consent was granted |
| `club_member` | `BOOLEAN` | `NOT NULL DEFAULT FALSE` | Whether customer is in the Club loyalty program |
| `club_points` | `INTEGER` | `NOT NULL DEFAULT 0` | Current Club points balance |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Account creation timestamp |
| `last_interaction` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Updated on every inbound message |

**Indexes:**

```sql
CREATE INDEX idx_customers_city ON mbb.customers (city);
CREATE INDEX idx_customers_opt_out ON mbb.customers (opt_out_flag) WHERE opt_out_flag = TRUE;
CREATE INDEX idx_customers_last_interaction ON mbb.customers (last_interaction DESC);
CREATE INDEX idx_customers_club ON mbb.customers (club_member) WHERE club_member = TRUE;
```

**Constraints:**

```sql
ALTER TABLE mbb.customers
  ADD CONSTRAINT chk_language CHECK (preferred_language IN ('lingala', 'french', 'swahili')),
  ADD CONSTRAINT chk_phone_format CHECK (phone_number ~ '^\+243[0-9]{9}$'),
  ADD CONSTRAINT chk_club_points CHECK (club_points >= 0);
```

**Business Rules:**
- `phone_number` is immutable after creation (natural key matching WhatsApp identity).
- `opt_out_flag = TRUE` is a system-wide kill switch — no relances, no proactive messages.
- `last_interaction` is updated on every inbound message (used for dormancy detection).
- Partial index on `opt_out_flag = TRUE` optimizes the "exclude opted-out" filter used in relance queries.

#### Table: `mbb.conversations`

**Purpose:** Manage individual chat sessions with context state.

| Column | Data Type | Constraints | Description |
|--------|-----------|-------------|-------------|
| `conversation_id` | `UUID` | `PRIMARY KEY DEFAULT gen_random_uuid()` | Unique session identifier |
| `customer_id` | `VARCHAR(20)` | `NOT NULL REFERENCES mbb.customers(phone_number) ON DELETE CASCADE` | Owning customer |
| `start_time` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Session start |
| `last_message_time` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Last activity (for dormancy) |
| `status` | `VARCHAR(20)` | `NOT NULL DEFAULT 'active'` | active, qualifying, nurturing, escalated, converted, dormant |
| `language_detected` | `VARCHAR(10)` | `NOT NULL` | Language sticky for this session |
| `context` | `JSONB` | `NOT NULL DEFAULT '{}'` | Flexible conversation state |
| `message_count` | `INTEGER` | `NOT NULL DEFAULT 0` | Total messages in this conversation |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Record creation |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Last update |

**JSONB `context` Structure (documented, not schema-enforced):**

```json
{
  "current_topic": "cable_2m",
  "stage": "consideration",
  "products_discussed": ["cable_2m", "powerbank_20k"],
  "price_discussed": true,
  "delivery_discussed": false,
  "qualification_step": 2,
  "persuasion_hooks_used": ["reciprocity", "social_proof"],
  "sb7_stage": "guide_gives_plan"
}
```

**Indexes:**

```sql
CREATE INDEX idx_conv_customer ON mbb.conversations (customer_id);
CREATE INDEX idx_conv_status ON mbb.conversations (status);
CREATE INDEX idx_conv_last_msg ON mbb.conversations (last_message_time DESC);
CREATE INDEX idx_conv_context ON mbb.conversations USING GIN (context jsonb_path_ops);
```

**Constraints:**

```sql
ALTER TABLE mbb.conversations
  ADD CONSTRAINT chk_conv_status CHECK (status IN ('active', 'qualifying', 'nurturing', 'escalated', 'converted', 'dormant')),
  ADD CONSTRAINT chk_conv_language CHECK (language_detected IN ('lingala', 'french', 'swahili'));
```

**Business Rules:**
- A customer can have multiple conversations (one active at a time, previous ones are dormant/converted).
- `language_detected` is set on first message and never changed within the same conversation.
- `context` JSONB is the synchronization target for Redis session cache (synced every 10 min).
- GIN index on `context` enables fast queries like `WHERE context @> '{"current_topic": "cable_2m"}'` for MAPS analysis.

#### Table: `mbb.messages`

**Purpose:** Store every inbound and outbound message (audit trail + MAPS source).

| Column | Data Type | Constraints | Description |
|--------|-----------|-------------|-------------|
| `message_id` | `UUID` | `PRIMARY KEY DEFAULT gen_random_uuid()` | Unique message ID |
| `conversation_id` | `UUID` | `NOT NULL REFERENCES mbb.conversations(conversation_id) ON DELETE CASCADE` | Parent conversation |
| `timestamp` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Message timestamp |
| `direction` | `VARCHAR(10)` | `NOT NULL` | inbound, outbound |
| `content` | `TEXT` | `NOT NULL` | Message text body |
| `content_type` | `VARCHAR(20)` | `NOT NULL DEFAULT 'text'` | text, voice_note, image |
| `language` | `VARCHAR(10)` | `NOT NULL` | Detected language |
| `persuasion_hook` | `VARCHAR(50)` | `NULL` | Blueprint hook applied (outbound only) |
| `processing_time_ms` | `INTEGER` | `NULL` | Time to generate response (outbound only) |
| `whatsapp_message_id` | `VARCHAR(100)` | `NULL` | External WhatsApp msg ID (inbound only) |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Record creation |

**Indexes:**

```sql
CREATE INDEX idx_msg_conversation ON mbb.messages (conversation_id);
CREATE INDEX idx_msg_timestamp ON mbb.messages (timestamp DESC);
CREATE INDEX idx_msg_direction ON mbb.messages (direction);
CREATE INDEX idx_msg_content_type ON mbb.messages (content_type) WHERE content_type != 'text';
CREATE INDEX idx_msg_fts ON mbb.messages USING GIN (to_tsvector('french', content));
```

**Constraints:**

```sql
ALTER TABLE mbb.messages
  ADD CONSTRAINT chk_msg_direction CHECK (direction IN ('inbound', 'outbound')),
  ADD CONSTRAINT chk_msg_content_type CHECK (content_type IN ('text', 'voice_note', 'image'));
```

**Partitioning Strategy (Phase 2):**

```sql
-- Partition by month for messages table (when volume exceeds 1M rows)
CREATE TABLE mbb.messages (
  -- ... same columns ...
) PARTITION BY RANGE (timestamp);

CREATE TABLE mbb.messages_2026_04 PARTITION OF mbb.messages
  FOR VALUES FROM ('2026-04-01') TO ('2026-05-01');
CREATE TABLE mbb.messages_2026_05 PARTITION OF mbb.messages
  FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');
```

**Business Rules:**
- Every inbound message generates at least 1 MAPS tag (enforced in application, not DB).
- `content_type = 'voice_note'` triggers immediate escalation (enforced in M1).
- Full-text search index enables MAPS pattern discovery across all messages.
- 90-day retention: messages older than 90 days archived to cold storage (Phase 2).

#### Table: `mbb.leads`

**Purpose:** Track qualified customers through the sales funnel.

| Column | Data Type | Constraints | Description |
|--------|-----------|-------------|-------------|
| `lead_id` | `UUID` | `PRIMARY KEY DEFAULT gen_random_uuid()` | Unique lead ID |
| `customer_id` | `VARCHAR(20)` | `NOT NULL REFERENCES mbb.customers(phone_number) ON DELETE CASCADE` | Owning customer |
| `conversation_id` | `UUID` | `NOT NULL REFERENCES mbb.conversations(conversation_id) ON DELETE CASCADE` | Qualifying conversation |
| `score` | `VARCHAR(10)` | `NOT NULL` | hot, warm, cold |
| `score_value` | `INTEGER` | `NOT NULL DEFAULT 0` | Numeric score (0–10) for granular ranking |
| `stage` | `VARCHAR(20)` | `NOT NULL DEFAULT 'awareness'` | awareness, consideration, decision |
| `intent` | `VARCHAR(30)` | `NOT NULL` | product_inquiry, support, club_loyalty |
| `product_interest` | `TEXT[]` | `NOT NULL DEFAULT '{}'` | Array of product IDs |
| `source` | `VARCHAR(50)` | `NOT NULL` | facebook_ad, spot_qr, referral, zone_event, organic |
| `relance_count` | `INTEGER` | `NOT NULL DEFAULT 0` | Current relance attempts (0–3) |
| `qualified_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | When lead was qualified |
| `last_nurture_at` | `TIMESTAMPTZ` | `NULL` | Last nurturing interaction |
| `converted_at` | `TIMESTAMPTZ` | `NULL` | When lead converted to order |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Record creation |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Last modification |

**Indexes:**

```sql
CREATE INDEX idx_leads_customer ON mbb.leads (customer_id);
CREATE INDEX idx_leads_score ON mbb.leads (score);
CREATE INDEX idx_leads_stage ON mbb.leads (stage);
CREATE INDEX idx_leads_relance ON mbb.leads (relance_count) WHERE relance_count < 3;
CREATE INDEX idx_leads_source ON mbb.leads (source);
CREATE INDEX idx_leads_qualified ON mbb.leads (qualified_at DESC);
CREATE UNIQUE INDEX idx_leads_conversation ON mbb.leads (conversation_id);
```

**Constraints:**

```sql
ALTER TABLE mbb.leads
  ADD CONSTRAINT chk_lead_score CHECK (score IN ('hot', 'warm', 'cold')),
  ADD CONSTRAINT chk_lead_stage CHECK (stage IN ('awareness', 'consideration', 'decision')),
  ADD CONSTRAINT chk_lead_relance CHECK (relance_count BETWEEN 0 AND 3),
  ADD CONSTRAINT chk_score_value CHECK (score_value BETWEEN 0 AND 10),
  ADD CONSTRAINT uq_lead_conversation UNIQUE (conversation_id);
```

**Business Rules:**
- 1 lead per conversation (unique constraint).
- `relance_count ≤ 3` is the hard constraint at DB level (application also checks).
- `score` is the categorical label; `score_value` is the numeric computation used by the scoring algorithm.
- Partial index on `relance_count < 3` optimizes the relance scheduler query ("find leads eligible for relance").
- `stage` progression is unidirectional (enforced in application — no DB trigger needed to avoid complexity).

#### Table: `mbb.relances`

**Purpose:** Track each strategic re-engagement attempt.

| Column | Data Type | Constraints | Description |
|--------|-----------|-------------|-------------|
| `relance_id` | `UUID` | `PRIMARY KEY DEFAULT gen_random_uuid()` | Unique relance ID |
| `lead_id` | `UUID` | `NOT NULL REFERENCES mbb.leads(lead_id) ON DELETE CASCADE` | Target lead |
| `attempt_number` | `INTEGER` | `NOT NULL` | 1, 2, or 3 |
| `scheduled_at` | `TIMESTAMPTZ` | `NOT NULL` | When relance should be sent |
| `delivered_at` | `TIMESTAMPTZ` | `NULL` | Actual delivery timestamp |
| `value_hook` | `TEXT` | `NOT NULL` | Personalized message content |
| `hook_type` | `VARCHAR(30)` | `NOT NULL` | reciprocity, social_proof, scarcity, loyalty |
| `response_received` | `BOOLEAN` | `NOT NULL DEFAULT FALSE` | Whether customer replied |
| `response_time_minutes` | `INTEGER` | `NULL` | Minutes between delivery and response |
| `cancelled` | `BOOLEAN` | `NOT NULL DEFAULT FALSE` | Cancelled due to opt-out |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Record creation |

**Indexes:**

```sql
CREATE INDEX idx_relance_lead ON mbb.relances (lead_id);
CREATE INDEX idx_relance_scheduled ON mbb.relances (scheduled_at) WHERE delivered_at IS NULL AND cancelled = FALSE;
CREATE INDEX idx_relance_performance ON mbb.relances (attempt_number, response_received);
```

**Constraints:**

```sql
ALTER TABLE mbb.relances
  ADD CONSTRAINT chk_relance_attempt CHECK (attempt_number BETWEEN 1 AND 3),
  ADD CONSTRAINT uq_relance_lead_attempt UNIQUE (lead_id, attempt_number);
```

**Business Rules:**
- Unique constraint on `(lead_id, attempt_number)` prevents duplicate relance for same attempt.
- Partial index on `delivered_at IS NULL AND cancelled = FALSE` optimizes the scheduler query (pending relances only).
- `response_time_minutes` is populated when customer replies after a relance (used for relance performance analytics).

#### Table: `mbb.maps_tags`

**Purpose:** Capture structured intelligence patterns from every interaction.

| Column | Data Type | Constraints | Description |
|--------|-----------|-------------|-------------|
| `tag_id` | `UUID` | `PRIMARY KEY DEFAULT gen_random_uuid()` | Unique tag ID |
| `message_id` | `UUID` | `NOT NULL REFERENCES mbb.messages(message_id) ON DELETE CASCADE` | Source message |
| `conversation_id` | `UUID` | `NOT NULL` | Denormalized for fast aggregation queries |
| `customer_id` | `VARCHAR(20)` | `NOT NULL` | Denormalized for per-customer analysis |
| `category` | `VARCHAR(30)` | `NOT NULL` | product_demand, silence_reason, conversion_trigger, language_usage, opt_out_reason |
| `pattern` | `VARCHAR(200)` | `NOT NULL` | Extracted pattern string |
| `trigger_event` | `VARCHAR(100)` | `NULL` | What caused this tag |
| `city` | `VARCHAR(50)` | `NULL` | Denormalized for city-level analytics |
| `language` | `VARCHAR(10)` | `NULL` | Denormalized for language breakdown |
| `metadata` | `JSONB` | `NOT NULL DEFAULT '{}'` | Flexible additional attributes |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Tag creation timestamp |

**Indexes:**

```sql
CREATE INDEX idx_maps_message ON mbb.maps_tags (message_id);
CREATE INDEX idx_maps_category ON mbb.maps_tags (category);
CREATE INDEX idx_maps_pattern ON mbb.maps_tags (pattern);
CREATE INDEX idx_maps_created ON mbb.maps_tags (created_at DESC);
CREATE INDEX idx_maps_city_category ON mbb.maps_tags (city, category);
CREATE INDEX idx_maps_metadata ON mbb.maps_tags USING GIN (metadata jsonb_path_ops);
```

**Constraints:**

```sql
ALTER TABLE mbb.maps_tags
  ADD CONSTRAINT chk_maps_category CHECK (category IN (
    'product_demand', 'silence_reason', 'conversion_trigger', 'language_usage', 'opt_out_reason'
  ));
```

**Denormalization Justification:**
- `conversation_id`, `customer_id`, `city`, `language` are denormalized from parent tables to avoid expensive JOINs on the highest-volume table (~10,000 inserts/day). This is the only intentional denormalization in the schema. Dashboard queries on MAPS data (M9) use these columns directly.

#### Table: `mbb.orders`

**Purpose:** Store conversion outcomes (completed purchases).

| Column | Data Type | Constraints | Description |
|--------|-----------|-------------|-------------|
| `order_id` | `UUID` | `PRIMARY KEY DEFAULT gen_random_uuid()` | Unique order ID |
| `lead_id` | `UUID` | `NOT NULL REFERENCES mbb.leads(lead_id) ON DELETE RESTRICT` | Converting lead |
| `customer_id` | `VARCHAR(20)` | `NOT NULL REFERENCES mbb.customers(phone_number) ON DELETE RESTRICT` | Buyer |
| `items` | `JSONB` | `NOT NULL` | `[{"product_id": "cable_2m", "quantity": 2, "unit_price": 15000}]` |
| `total_amount` | `DECIMAL(12, 2)` | `NOT NULL` | Total in Congolese Francs (FC) |
| `currency` | `VARCHAR(3)` | `NOT NULL DEFAULT 'CDF'` | ISO 4217 currency code |
| `payment_type` | `VARCHAR(20)` | `NOT NULL` | mobile_money, bank_transfer, cod |
| `delivery_zone` | `VARCHAR(50)` | `NOT NULL` | Gombe, Limete, etc. |
| `delivery_method` | `VARCHAR(20)` | `NOT NULL DEFAULT 'moto_taxi'` | moto_taxi, spot_pickup |
| `status` | `VARCHAR(20)` | `NOT NULL DEFAULT 'pending'` | pending, confirmed, preparing, delivering, delivered, cancelled |
| `hub_crm_synced` | `BOOLEAN` | `NOT NULL DEFAULT FALSE` | Synced to Airtable |
| `hub_crm_order_id` | `VARCHAR(50)` | `NULL` | Airtable record ID |
| `club_points_credited` | `INTEGER` | `NOT NULL DEFAULT 0` | Points awarded for this order |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Order creation |
| `confirmed_at` | `TIMESTAMPTZ` | `NULL` | Payment confirmed |
| `delivered_at` | `TIMESTAMPTZ` | `NULL` | Delivery completed |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Last status change |

**Indexes:**

```sql
CREATE INDEX idx_orders_lead ON mbb.orders (lead_id);
CREATE INDEX idx_orders_customer ON mbb.orders (customer_id);
CREATE INDEX idx_orders_status ON mbb.orders (status);
CREATE INDEX idx_orders_created ON mbb.orders (created_at DESC);
CREATE INDEX idx_orders_hub_sync ON mbb.orders (hub_crm_synced) WHERE hub_crm_synced = FALSE;
```

**Constraints:**

```sql
ALTER TABLE mbb.orders
  ADD CONSTRAINT chk_order_payment CHECK (payment_type IN ('mobile_money', 'bank_transfer', 'cod')),
  ADD CONSTRAINT chk_order_status CHECK (status IN ('pending', 'confirmed', 'preparing', 'delivering', 'delivered', 'cancelled')),
  ADD CONSTRAINT chk_order_delivery CHECK (delivery_method IN ('moto_taxi', 'spot_pickup')),
  ADD CONSTRAINT chk_order_amount CHECK (total_amount > 0);
```

**State Machine (order status):**

```
pending ──→ confirmed ──→ preparing ──→ delivering ──→ delivered
   │                                                       
   └──→ cancelled (from any state except delivered)
```

**Business Rules:**
- `ON DELETE RESTRICT` on customer and lead FKs prevents accidental deletion of customers who have orders.
- Partial index on `hub_crm_synced = FALSE` speeds up the Celery sync task (find unsynced orders).
- `total_amount` stored in Congolese Francs (CDF). Conversion to USD only in dashboard (M9).

#### Table: `mbb.escalation_tickets`

| `conversation_id` | `UUID` | `NOT NULL REFERENCES mbb.conversations(conversation_id) ON DELETE CASCADE` | Source conversation |
| `customer_id` | `VARCHAR(20)` | `NOT NULL REFERENCES mbb.customers(phone_number) ON DELETE CASCADE` | Escalated customer |

| `reason` | `VARCHAR(50)` | `NOT NULL` | voice_note, complex_complaint, high_value_lead, unresolved_3x, sav_issue |
| `assigned_to` | `VARCHAR(100)` | `NULL` | Hub Team member |
| `status` | `VARCHAR(20)` | `NOT NULL DEFAULT 'open'` | open, in_progress, resolved, closed |

| `transcript_snapshot` | `JSONB` | `NOT NULL` | Last 10 messages at time of escalation |
| `maps_tags_snapshot` | `JSONB` | `NULL` | MAPS tags applied to conversation |
| `created_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Escalation creation |
| `assigned_at` | `TIMESTAMPTZ` | `NULL` | When Hub member picked up |
| `resolved_at` | `TIMESTAMPTZ` | `NULL` | Resolution timestamp |

**Indexes:**

```sql
CREATE INDEX idx_esc_conversation ON mbb.escalation_tickets (conversation_id);
CREATE INDEX idx_esc_customer ON mbb.escalation_tickets (customer_id);
CREATE INDEX idx_esc_status ON mbb.escalation_tickets (status) WHERE status IN ('open', 'in_progress');
CREATE INDEX idx_esc_priority ON mbb.escalation_tickets (priority, created_at DESC);
```

**Constraints:**

```sql
ALTER TABLE mbb.escalation_tickets
  ADD CONSTRAINT chk_esc_priority CHECK (priority IN ('high', 'medium', 'low')),
  ADD CONSTRAINT chk_esc_status CHECK (status IN ('open', 'in_progress', 'resolved', 'closed'));
```

**Business Rules:**
- `transcript_snapshot` captures the last 10 messages as JSONB so Hub Team has full context without querying the messages table.
- `priority = 'high'` auto-assigned for voice notes and high-value leads.
- SLA: `created_at` to `assigned_at` must be < 3 minutes (monitored by M9).

|--------|-----------|-------------|-------------|
| `product_id` | `VARCHAR(50)` | `PRIMARY KEY` | Unique product identifier (from BOX) |
| `name` | `VARCHAR(200)` | `NOT NULL` | Product display name |

| `is_active` | `BOOLEAN` | `NOT NULL DEFAULT TRUE` | Product available for sale |
| `updated_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT NOW()` | Last modification |

**Sync Strategy:**
- Full catalog refresh: every 6 hours (Celery Beat scheduled task).
- Stock levels: every 30 minutes (lightweight poll).
- Price changes: real-time via MBB BOX webhook (if available), else hourly poll.
- If BOX is unreachable, the last cached data is used (graceful fallback).

> **Design Principle:** These tables are **additive** — they do not modify existing Phase 1 tables. M5 and M7 modules interact with these tables through the adapter interfaces defined in Module Component Design Section 8.

## Appendix: DRC-Specific Considerations

- **Character Encoding**: UTF-8 required for Lingala (ə, ɔ, ǝ), Swahili, and French accents

- **Phone Format**: E.164 format strictly enforced `+243XXXXXXXXX` (10-digit DRC numbers)
- **Collation**: French collation `fr_CD.UTF-8` used for text indexing and string comparisons

#### View: `mbb.mv_daily_maps_summary`

**Purpose:** Pre-aggregated MAPS data for dashboard (M9). Avoids expensive scans on `maps_tags`.

```sql
CREATE MATERIALIZED VIEW mbb.mv_daily_maps_summary AS
SELECT
  DATE_TRUNC('day', created_at) AS day,
  category,
  pattern,
  city,
  language,
  COUNT(*) AS tag_count
FROM mbb.maps_tags
WHERE created_at > NOW() - INTERVAL '90 days'
GROUP BY 1, 2, 3, 4, 5
ORDER BY day DESC, tag_count DESC;

CREATE UNIQUE INDEX idx_mv_maps_day ON mbb.mv_daily_maps_summary (day, category, pattern, city, language);

-- Refresh schedule: daily at 02:00 UTC via pg_cron
SELECT cron.schedule('refresh_maps_summary', '0 2 * * *', 'REFRESH MATERIALIZED VIEW CONCURRENTLY mbb.mv_daily_maps_summary');
```

#### View: `mbb.mv_funnel_metrics`

**Purpose:** Pre-computed conversion funnel for dashboard.

```sql
CREATE MATERIALIZED VIEW mbb.mv_funnel_metrics AS
SELECT
  DATE_TRUNC('day', l.qualified_at) AS day,
  l.source,
  l.score,
  l.stage,
  COUNT(*) AS lead_count,
  COUNT(o.order_id) AS converted_count,
  ROUND(COUNT(o.order_id)::NUMERIC / NULLIF(COUNT(*), 0) * 100, 1) AS conversion_rate
FROM mbb.leads l
LEFT JOIN mbb.orders o ON o.lead_id = l.lead_id AND o.status != 'cancelled'
WHERE l.qualified_at > NOW() - INTERVAL '90 days'
GROUP BY 1, 2, 3, 4
ORDER BY day DESC;

CREATE UNIQUE INDEX idx_mv_funnel_day ON mbb.mv_funnel_metrics (day, source, score, stage);
```

### 2.7 Data Integrity & Consistency Rules

| Rule | Enforcement Level | Mechanism |
|------|-------------------|-----------|
| Max 3 relances per lead | DB + Application | CHECK constraint + pre-insert validation |
| 1 lead per conversation | DB | UNIQUE constraint on `conversation_id` |
| 1 payment per order | DB | UNIQUE index on `order_id` |
| Opt-out blocks all relances | Application | Check `opt_out_flag` before scheduling |
| Stage progression is unidirectional | Application | Validate `new_stage > current_stage` |
| Order amount > 0 | DB | CHECK constraint |
| Phone number format E.164 | DB + Application | CHECK regex + Pydantic validator |
| No message loss | Infrastructure | Redis AOF + dead-letter queue |
| Session ↔ DB consistency | Application | Redis-to-PostgreSQL sync every 10 min |
