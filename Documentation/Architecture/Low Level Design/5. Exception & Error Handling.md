# 5. Exception & Error Handling

## Purpose

This document defines the error handling framework for the MBB ya Kin system. It classifies errors into 5 categories (client, server, external, business rule, infrastructure), provides 35+ standard error codes with HTTP status mappings, specifies retry logic and circuit breaker patterns, and defines graceful degradation strategies. All error responses follow a consistent JSON schema.

## Audience

- **Backend Developers**: Implement error handling according to these codes and patterns
- **Operations Teams**: Use error codes for monitoring, alerting, and troubleshooting
- **Frontend/Dashboard Teams**: Display error messages to end users appropriately
- **QA/Testing**: Validate error handling for each error code

---

### 5.1 Error Handling Philosophy

Error handling in MBB ya Kin follows these principles:

1. **Never fail silently** — all errors are logged with full context.
2. **Graceful degradation** — system reduces functionality instead of crashing completely.
3. **Customer-first messaging** — errors expose helpful messages to customers (in their language), not stack traces.
4. **Automated recovery** — transient errors trigger automated retry logic.
5. **Fail-fast for invalid input** — validation errors return immediately with clear feedback.
6. **Circuit breakers for external dependencies** — prevent cascade failures.

---

### 5.2 Error Classification

Errors are classified into 5 categories, each with different handling strategies:

| Category | Code Range | Source Examples | Handling Strategy |
|----------|------------|-----------------|-------------------|
| **Client Errors** | 4xx-CLIENT | Invalid request payloads, validation failures | Immediate 400 response with validation details |
| **Server Errors** | 5xx-SERVER | Unhandled exceptions, database crashes | Log error, return 500, alert ops team |
| **External Errors** | EXT-xxx | Claude API timeout, Mobile Money webhook failure | Circuit breaker + retry logic + fallback response |
| **Business Rule Violations** | BIZ-xxx | Max relance exceeded, opt-out detected | Return 400 with business rule message |
| **Infrastructure Errors** | INFRA-xxx | Redis unreachable, PostgreSQL connection pool exhausted | Graceful degradation + alert |

### 5.4 Error Response Format

All error responses follow a consistent JSON schema:

```json
{
  "error": {
    "code": "CLIENT-001",
    "message": "Invalid phone number format. Must be E.164 (+243XXXXXXXXX).",
    "http_status": 400,
    "details": {
      "field": "customer_phone",
      "expected": "^\\+243[0-9]{9}$",
      "received": "0987654321"
    },
    "timestamp": "2026-04-14T15:00:00Z",
    "request_id": "uuid"
  }
}
```

**Field Descriptions:**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `code` | string | Yes | Internal error code from Section 5.3 |
| `message` | string | Yes | Human-readable error message (English) |
| `http_status` | integer | Yes | HTTP status code |
| `details` | object | No | Contextual information (field name, expected/received values) |
| `timestamp` | ISO 8601 | Yes | Error occurrence timestamp |
| `request_id` | UUID | Yes | Request trace ID for debugging |

**Pydantic Model:**

```python
class ErrorDetailDTO(BaseModel):
    field: str | None = None
    expected: str | None = None
    received: str | None = None
    context: dict[str, Any] | None = None

class ErrorResponseDTO(BaseModel):
    error: ErrorDTO

class ErrorDTO(BaseModel):
    code: str
    message: str
    http_status: int
    details: ErrorDetailDTO | None = None
    timestamp: datetime = Field(default_factory=lambda: datetime.now(timezone.utc))
    request_id: UUID
```

### 5.5 Retry & Circuit Breaker Patterns

#### 5.5.1 Retry Logic

**Exponential Backoff Formula:**

```
retry_delay = min(base_delay × 2^(attempt - 1), max_delay) + random_jitter
```

| Dependency | Max Retries | Base Delay | Max Delay | Jitter |
|------------|-------------|------------|-----------|--------|
| Claude API | 3 | 2s | 16s | ±500ms |
| PostgreSQL (transient) | 3 | 1s | 8s | ±200ms |
| Redis (transient) | 2 | 500ms | 2s | ±100ms |
| Celery task | 3 | 5s | 30s | ±1s |
| Mobile Money webhook delivery | 3 | 10s | 60s | ±2s |

**Retry Decision Tree:**

```python
def should_retry(error: Exception, attempt: int) -> bool:
    if attempt >= MAX_RETRIES:
        return False
    
    # Retry on transient errors
    if isinstance(error, (TimeoutError, ConnectionError, HTTPStatusError)):
        if hasattr(error, 'status_code') and error.status_code in [429, 500, 502, 503, 504]:
            return True
    
    # Do NOT retry on client errors (4xx except 429)
    if hasattr(error, 'status_code') and 400 <= error.status_code < 500 and error.status_code != 429:
        return False
    
    return True
```

**Idempotency Keys:** All retry logic uses `X-Idempotency-Key` header to ensure safe retries on POST/PUT operations.

#### 5.5.2 Circuit Breaker

**Implementation:** Using `circuitbreaker` library for Python.

| Dependency | Failure Threshold | Recovery Timeout | Half-Open Requests |
|------------|-------------------|------------------|---------------------|
| Claude API | 5 failures in 60s | 30s | 1 |
| PostgreSQL | 3 failures in 30s | 60s | 1 |
| Celery (task queue) | 5 failures in 60s | 30s | 1 |
| MBB HUB API (Phase 2) | 5 failures in 60s | 30s | 1 |
| MBB BOX API (Phase 2+) | 5 failures in 60s | 30s | 1 |

**Circuit States:**

1. **CLOSED (normal):** All requests pass through. Failure counter resets every 60s.
2. **OPEN (failing):** All requests immediately fail with 503. No actual calls to dependency.
3. **HALF_OPEN (testing recovery):** 1 request allowed through. If success → CLOSED. If failure → OPEN.

**Example Implementation:**

```python
from circuitbreaker import circuit

@circuit(failure_threshold=5, recovery_timeout=30, expected_exception=HTTPError)
async def call_claude_api(prompt: str) -> str:
    async with httpx.AsyncClient() as client:
        response = await client.post(
            CLAUDE_API_URL,
            json={"prompt": prompt, "max_tokens": 150},
            timeout=30.0
        )
        response.raise_for_status()
        return response.json()['completion']

# Usage with fallback
try:
    ai_response = await call_claude_api(prompt)
except CircuitBreakerError:
    logger.warning("Claude API circuit breaker OPEN. Using fallback.")
    ai_response = FALLBACK_RESPONSES[language][context_stage]
```

### 5.6 Graceful Degradation Strategy

When external dependencies fail, the system degrades functionality instead of failing completely:

| Failed Dependency | Degraded Behavior | User Experience |
|------------------|-------------------|-----------------|
| **Claude API** | Use pre-defined template responses based on conversation stage + language | Customer receives helpful response (not AI-generated), conversation continues |
| **Redis (cache)** | Read directly from PostgreSQL, skip session caching | Slightly slower responses (<1s increase), no data loss |
| **PostgreSQL** | Queue all writes to Redis, return 202 Accepted | Messages queued, processed once DB recovers |
| **Celery (task queue)** | Store outbound messages in database, retry delivery every 5 min | Messages delayed but eventually delivered |
| **Mobile Money webhook** | Manual confirmation by Hub Team via dashboard | Order fulfillment continues, payment confirmation manual || **MBB HUB (Phase 2)** | Fallback to AirtableAdapter for CRM sync; queue failed syncs for retry | No visible impact on customer; orders/leads sync when HUB recovers |
| **MBB BOX (Phase 2+)** | Fallback to static product catalog (cached JSON) | Customer receives last-known pricing/stock; slightly stale data possible |

### 5.7 Dead-Letter Queue (DLQ) Handling

Messages that fail processing after 3 retry attempts are moved to a dead-letter queue for manual intervention:

**DLQ Structure (Redis List):**

```
Key: queue:messages:dead_letter
Type: LIST
Payload: {
  "original_message": {...},
  "failure_reason": "Claude API timeout after 3 retries",
  "error_code": "EXT-CLAUDE-001",
  "attempts": 3,
  "first_attempt_at": "2026-04-14T14:30:00Z",
  "last_attempt_at": "2026-04-14T14:32:00Z",
  "stack_trace": "..."
}
```

**DLQ Monitoring:**
- Alert triggered when DLQ depth > 10.
- Critical alert when DLQ depth > 100 (requires immediate ops intervention).
- Dashboard displays DLQ messages with "Retry" and "Discard" buttons.

**Manual Retry Flow:**
1. Ops team reviews DLQ message in dashboard.
2. If transient (Claude API was down temporarily) → Click "Retry" → re-queue to `queue:messages:pending`.
3. If permanent failure (invalid payload, business rule violation) → Click "Discard" + "Notify Customer" → send apology message via Celery task.

#### 5.8.3 PII Redaction in Logs

All logs automatically redact PII before writing:

| Field | Redaction Rule |
|-------|----------------|
| `customer_phone` | Mask middle digits: `+243987654321` → `+243******321` |
| `customer_name` | Redact completely: `Jean Mukendi` → `[REDACTED]` |
| `message_content` | First 50 chars only, rest replaced with `...` |
| `payment_transaction_id` | Keep (not PII, needed for debugging) |
| `whatsapp_message_id` | Keep (not PII) |
| All JSONB context fields | Redact any field matching `name`, `address`, `email` keys |

**Implementation:**

```python
import logging
import re

class PIIRedactingFormatter(logging.Formatter):
    PHONE_PATTERN = re.compile(r'(\+243)(\d{3})(\d{4})(\d{2})')
    
    def format(self, record):
        msg = super().format(record)
        # Redact phone numbers
        msg = self.PHONE_PATTERN.sub(r'\1******\4', msg)
        # Redact names (simple heuristic: capitalized words in specific contexts)
        msg = re.sub(r'"customer_name":\s*"[^"]*"', '"customer_name": "[REDACTED]"', msg)
        return msg

logger = logging.getLogger('mbb')
handler = logging.StreamHandler()
handler.setFormatter(PIIRedactingFormatter('%(message)s'))
logger.addHandler(handler)
```

### 5.11 Exception Handling by Module

#### Module-Specific Handlers:

| Module | Expected Exceptions | Handling Strategy |
|--------|---------------------|-------------------|
| **M1 (WhatsApp Gateway)** | `InvalidPhoneNumberError`, `RateLimitExceededError`, `DuplicateMessageError` | Return 400 with error code, log, do NOT retry |
| **M2 (Language Detection)** | `LanguageDetectionTimeoutError` | Default to French, log warning |

| **M4 (Conversation Engine)** | `ClaudeAPITimeoutError`, `SessionDeserializationError`, `ContextTooLargeError` | Retry Claude (3x with exponential backoff), fallback on failure; clear session on deserialize error |
| **M5 (Lead Qualification)** | `DuplicateLeadError`, `InvalidStageTransitionError` | Return 400/409 with business rule message |
| **M6 (Relance Engine)** | `MaxRelanceExceededError`, `BlackoutHourError`, `OptOutDetectedError` | Return 400 with BIZ code, cancel relance |
| **M7 (Conversion & Order)** | `PaymentAmountMismatchError`, `InvalidOrderStateTransitionError`, `HubCRMSyncError`, `MBBHubSyncError` (Phase 2), `MBBBoxStockError` (Phase 2+) | Return 400 for validation; retry Hub CRM sync (3x), manual fallback on failure; fallback to Airtable if HUB unreachable; fallback to static catalog if BOX unreachable |
| **M8 (MAPS Intelligence)** | `MAPSTagInsertError` | Log error, continue processing (MAPS capture is non-critical) |
| **M9 (Analytics Dashboard)** | `QueryTimeoutError`, `MaterializedViewStaleError` | Return cached result (stale data acceptable), refresh async |

### 5.12 Error Handling Checklist (Implementation)

For every new endpoint or module function:

- [ ] **Input Validation:** Use Pydantic models with explicit validators.
- [ ] **Error Wrapping:** Catch low-level exceptions, wrap in custom exceptions with error codes.
- [ ] **Logging:** Log all errors with structured context (conversation_id, customer_phone, request_id).
- [ ] **PII Redaction:** Ensure phone numbers and names are masked in logs.
- [ ] **Customer Message:** Return helpful, language-appropriate message (not stack trace).
- [ ] **Retry Logic:** Implement exponential backoff for transient errors.
- [ ] **Circuit Breaker:** Apply to all external API calls.
- [ ] **Idempotency:** Use `X-Idempotency-Key` for POST/PUT operations.
- [ ] **Monitoring:** Emit error metrics to Prometheus.
- [ ] **DLQ:** Move failed messages to dead-letter queue after max retries.
- [ ] **Graceful Degradation:** Define fallback behavior when dependency fails.
