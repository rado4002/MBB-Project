**External Actors:**

1. **Customer (Primary Actor):**
   - Sends WhatsApp messages in Lingala/French/Swahili hybrid
   - Receives responses, product recommendations, payment instructions
   - Expects <60s response time, warm tone

2. **Hub Team (Human Support):**
   - Receives escalations (voice notes, complex issues, high-value leads)
   - Hands off orders to system after conversion
   - Monitors queue during blackouts

3. **Lab Team (Intelligence Consumer):**
   - Queries MAPS insights for product development
   - Conducts weekly tone audits
   - Reviews silence patterns and conversion triggers

4. **Toronto Supervision (Business Intelligence):**
   - Views dashboard (funnel, relance performance, language breakdown)
   - Exports analytics to CSV/Google Sheets
   - Monitors KPIs (conversion rate, automation %, opt-out rate)

5. **WhatsApp Business API (Channel):**
   - Delivers inbound messages
   - Sends outbound responses
   - Primary communication channel (100% of traffic)

6. **Mobile Money Providers (Payment):**
   - Orange Money, Airtel Money, M-Pesa
   - Receive payment requests
   - Send confirmation callbacks

7. **Hub CRM/Airtable (Order Management):**
   - Receives order records
   - Updates Club points
   - Tracks inventory

8. **Logistics API (Delivery):**
   - Provides delivery zone info
   - Handles COD scheduling
   - Manages Spot pickup routing

9. **MBB HUB (Phase 2 — CRM Replacement):**
   - Replaces Airtable as primary CRM backend
   - Customer data sync, lead routing, order management
   - Club points and loyalty program management
   - Escalation queue for Hub Team
   - Connected via MBBHubAdapter (Adapter Pattern)

10. **MBB BOX (Phase 2+ — Inventory System):**
    - Real-time product stock levels by city/zone
    - Dynamic pricing updates
    - Product catalog and availability checks
    - Connected via MBBBoxAdapter (Adapter Pattern)
    - Graceful fallback to static catalog if unreachable

11. **Digital Presence Platform (Brand & Acquisition):**
   - Owns Facebook, Instagram, TikTok, and future website/CMS presence
   - Manages paid ads, content publishing, reels/videos/images, and landing pages
   - Feeds leads into the bot via click-to-WhatsApp, forms, and future web chat/widget
   - Stays outside the bot core so marketing operations do not overload CRM or inventory modules

**Key Interactions:**
- **Inbound:** Customer messages → WhatsApp API → MBB ya Kin
- **Outbound:** MBB ya Kin → WhatsApp API → Customer responses
- **Escalation:** MBB ya Kin → Hub Team (complex cases)
- **Intelligence:** MBB ya Kin → Lab Team (MAPS data)
- **Payment:** MBB ya Kin → Mobile Money API → Customer confirmation
- **Orders:** MBB ya Kin → Hub CRM → fulfillment
- **CRM Sync (Phase 2):** MBB ya Kin → MBB HUB (leads, orders, Club points)
- **Inventory (Phase 2+):** MBB ya Kin → MBB BOX (stock, pricing, catalog)
- **Lead Acquisition:** Digital Presence Platform → MBB ya Kin (ads, forms, click-to-WhatsApp, future web chat)

### 6.3 Domain Model (Business Entities & Relationships)

Core business entities: Customer, Conversation, Lead, Message, Relance, MAPS Tag, Lab Insight, Order, Payment

**Relationships:**
- Customer **has** multiple Conversations (1:*)
- Conversation **contains** multiple Messages (*:*)
- Customer **becomes** Lead once qualified (1:1)
- Lead **triggers** Relances (1:*, max 3)
- Message **generates** MAPS Tags (1:*)
- Lead **converts to** Order (1:0..1)
- Order **fulfills via** Payment (1:1)

**Business Rules:**
- Max 3 relances per lead (hard constraint)
- Opt-out flag prevents all future relances
- Language: auto-detected from first message, sticky per conversation
- MAPS: 100% interaction capture (every message generates at least one tag)

### 6.4 Class Diagram (Refined Structural Design)

**Service Layer:**
- `ConversationManager`: Orchestrates conversation flow
- `PersuasionEngine`: Applies Blueprint principles (Cialdini, SB7, ERRC, Hormozi)
- `LeadQualificationService`: Scores and qualifies leads
- `RelanceEngine`: Manages strategic re-engagement (max 3 rule, value-first)
- `MAPSIntelligenceService`: Captures and analyzes patterns
- `EscalationService`: Determines when to escalate to humans

**Repository Layer:**
- `ConversationRepository`: Manages conversation persistence
- `LeadRepository`: Manages lead data + funnel stats
- `MAPSRepository`: Stores and queries MAPS tags

**Design Principles:**
- Separation of Concerns (entities, services, repositories)
- Single Responsibility (each service has one reason to change)
- Dependency Inversion (services depend on repository interfaces)
- Encapsulation (business rules enforced in methods)

### 6.6 Sequence Diagrams (Runtime Behavior)

#### Scenario 1: First Message from New Customer (Happy Path)
- Receive message in Lingala
- Detect language
- Create customer and conversation
- Generate culturally-appropriate response with persuasion hook
- Capture MAPS tag
- **Total time:** 3–5 seconds (target: <60s ✓)

#### Scenario 2: Lead Qualification & Nurturing Flow
- Score lead (WARM)
- Ask contextual questions (location, intent)
- Advance stage (AWARENESS → CONSIDERATION → DECISION)
- Nurture with product recommendations
- Initiate conversion (payment options)

#### Scenario 3: Blackout Recovery (Resilience)
- Customer sends message (internet goes down)
- Message queued in Redis (zero loss)
- Send acknowledgment (holding response)
- FastAPI comes online
- Process queued messages with restored context
- Customer resumes conversation naturally

#### Scenario 4: Strategic Relance (Re-engagement)
- Lead silent > 24h
- Scheduler checks eligibility (relance_count < 3, opt_out = false)
- Generate personalized value hook
- Respect blackout hours (no 22:00–07:00 relances)
- Send relance #1 → max 3 attempts per lead

#### Scenario 5: Human Escalation
- Customer sends voice note
- Immediately escalate (voice = high priority)
- Notify Hub Team with full context
- Send acknowledgment to customer
- Hub team takes over conversation
- Capture escalation reason as MAPS tag

## 7. Technology Stack Selection

Structured 6-phase decision process to select optimal technology stack aligned with architecture, requirements, and constraints.

### 7.1 Architectural Style Alignment

**Selected Style:** Layered + Event-Driven Hybrid

**Imposed Constraints:**
- Layered architecture: Clear separation (presentation, business, data, observability)
- Event-driven: Asynchronous messaging with persistent queues
- Scalability: Horizontal scaling (stateless business layer)
- Communication: Synchronous REST (critical path), asynchronous queues (resilience)
- Deployment: Self-hosted, Docker-based, Kubernetes-ready (Phase 2)

**Eliminated Technologies:**
- ❌ Serverless (AWS Lambda): Violates self-hosted constraint
- ❌ GraphQL: REST sufficient for WhatsApp webhook patterns
- ❌ gRPC: Unnecessary complexity for current scale
- ❌ NoSQL (MongoDB): MAPS analytics need SQL joins
- ❌ MQTT: WhatsApp uses HTTP, not IoT protocols

### 7.3 Technical Evaluation & Filtering

#### **Dashboard Layer**
- **Selected:** ✅ **Streamlit** (Python-native, rapid prototyping, direct PostgreSQL)
- Alternative: Dash (more complex, less Python-friendly)
- Eliminated: Grafana (overkill), React (development overhead)

#### **Backend Layer**
- **Selected:** ✅ **FastAPI** (async-native, type hints, LLM ecosystem)
- Alternative: None
- Eliminated: Flask (sync by default, NFR1 risk), Django (too heavyweight), Go (weaker LLM libs)

#### **Orchestration Layer**
- **Selected:** ✅ **Celery + Celery Beat** (Python-native, uses Redis broker, async task processing)
- Alternative: None
- Eliminated: n8n (extra Node.js service, 500MB+ RAM, added failure point), Airflow (code-first DAGs, technical complexity), Temporal (steep curve)

#### **Database Layer**
- **Selected:** ✅ **PostgreSQL** (ACID, JSONB, full-text search, mature)
- Alternative: None
- Eliminated: MongoDB (MAPS analytics need joins), MySQL (weaker JSON), SQLite (concurrency issues)

#### **Cache/Queue Layer**
- **Selected:** ✅ **Redis** (dual-purpose cache+queue, AOF persistence, sub-ms latency)
- Alternative: None
- Eliminated: Memcached (no persistence), RabbitMQ/Kafka (overkill, higher ops cost)

#### **LLM Layer**
- **Selected:** ✅ **Claude Sonnet 3.5** (multilingual, low latency, reasonable cost)
- Fallback: Gemini Pro (free tier available)
- Eliminated: GPT-4 (2x cost, no advantage), LLaMA 3 (GPU cost + latency)

#### **Infrastructure Layer**
- **Phase 1:** ✅ **Docker Compose** (simple, sufficient for single-node)
- **Phase 2:** ✅ **Kubernetes** (multi-node scaling)
- Eliminated: Podman (smaller ecosystem), Nomad (niche)

#### **Monitoring Layer**
- **Selected:** ✅ **Prometheus + Grafana** (industry standard)
- Alternative: Loki (logs), OpenTelemetry (traces)
- Eliminated: ELK (resource-intensive)

### 7.7 Stack Rationale Summary

**Why This Stack Solves MBB ya Kin:**
