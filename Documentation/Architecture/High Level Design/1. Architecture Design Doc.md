1. Architectural Analysis

1.1 Key Functional Requirements (FRs) and Non-Functional Requirements (NFRs)

Core FRs driving architecture (from Requirements v1.1):

* Real-time message reception/processing (<60 s) and multi-language auto-detection/hybrid response (FR1–FR2).
* Conversation context management, lead qualification, nurturing, in-chat ordering, and payment/logistics integration (FR3–FR6).
* Strategic relance engine (max 3, value-first, culturally adapted) with opt-out (FR7).
* Automatic MAPS intelligence capture and tagging from every interaction (FR8).
* Intelligent escalation, queue/resilience handling (blackout recovery), analytics/dashboard, and privacy/consent (FR9–FR12).

Core NFRs driving architecture:

* Performance: <60 s first response, minimal latency, high concurrent volume (NFR1).
* Reliability/Resilience: Unstable networks, power outages, ≥95 % uptime, no message loss (NFR2).
* Scalability: Horizontal scaling, multi-city support (Kinshasa, Lubumbashi, Goma) (NFR3).
* Usability/Cultural Accuracy: Human, short, emoji-friendly, weekly tone audits (NFR4–NFR5).
* Maintainability, Extensibility, Security/Privacy, Observability (NFR6–NFR12).

1.2 Architecturally Significant Requirements (ASRs)

The following ASRs shape every design decision:

* Ultra-low latency + resilience in hostile infrastructure: Blackout queuing, graceful resume, and recovery messaging must be first-class (directly addresses RDC realities and 30–40 % lost-revenue risk).
* Cultural proximity + persuasion intelligence: Every response must embed Cialdini, StoryBrand SB7, Blue Ocean ERRC, and Hormozi principles without feeling robotic (weekly audits required).
* Intelligence-first data loop: 100 % of interactions must auto-generate structured MAPS tags (product demand, silence reasons, persuasion triggers) in real time.
* Ethical guardrails at system level: Strict max-3 relances, universal opt-out (“stop/arrête/non”), consent-first, minimal data.
* Self-hosted, low-resource constraint: No cloud dependency; must run on modest infrastructure.

1.3 Constraints

* Technical: WhatsApp Business API only (primary channel); low-bandwidth-first (text-primary); fully self-hosted/Dockerized.
* Business: Must preserve “helpful young Congolese friend” tone; integrate with existing Hub CRM/Airtable for orders/Club points; support Mobile Money + COD + Spot pickup routing.
* Environmental: Frequent blackouts, unstable 3G/4G, high mobility, hybrid Lingala/French/Swahili communication, price-sensitive/inflation-aware users.
* Regulatory/Ethical: Privacy by design, explicit consent, data minimization, anti-spam (NFR12).

1.4 Risks and Trade-offs

Blackout-induced message loss	High	High 2	Redis queue + retry (trade-off: slight added latency during restore)
Robotic tone drift	Medium	High	Weekly MAPS-driven tone audits + master prompt guardrails (adds Lab overhead)
High-volume spikes overwhelming queue	Medium	Medium	Rate limiting + horizontal scaling (trade-off: temporary queuing for non-critical messages)
Language detection errors in hybrids	Medium	Medium	French fallback + escalation path (trade-off: minor user friction <5 %)
Over-persuasion triggering opt-outs	Low	High	Strict 3-touch rule + value-first blueprint enforcement

The system follows a Layered + Event-Driven hybrid conceptual structure that is deliberately technology-agnostic at this level. It separates concerns to achieve high cohesion, low coupling, resilience, and extensibility.

This conceptual model directly satisfies ASRs for resilience (queue), intelligence (MAPS events), and extensibility (pluggable channels).

4. Design Patterns Selection

The architecture deliberately combines four complementary patterns:

1. Layered Architecture (primary structural pattern) Justification: Provides clear separation of concerns (presentation/interaction, business, data, observability). Directly supports NFR7 (maintainability) and NFR8 (extensibility). Allows weekly tone audits to touch only the Intelligence layer without touching core flows.
2. Event-Driven Architecture (with asynchronous messaging) Justification: Enables blackout resilience (FR10), decoupling of relance timing (FR7), and real-time MAPS capture (FR8). Events ensure no message loss and graceful resume. Chosen over synchronous calls to meet NFR2 (reliability under unstable networks).
3. Saga Pattern (for long-running conversational flows) Justification: Manages the multi-step customer journey (qualification → nurture → conversion → relance) with state persistence. Handles compensation (e.g., opt-out cancels pending relance saga). Aligns with StoryBrand SB7 and Hormozi 4-pillars rhythm.
4. Repository + Strategy Patterns (for MAPS & Persuasion) Justification: MAPS tagging is a strategy that can evolve (new Blueprint elements added without changing core logic). Repository abstracts persistence so Lab can query patterns independently. Supports FR8 and weekly audits (NFR5).

Why these patterns together?

They achieve the required quality attributes:

* Performance & Resilience → Event-Driven + Queue.
* Cultural/Persuasion Accuracy → Strategy pattern isolates Blueprint logic.
* Scalability & Maintainability → Layered + low coupling.
* Traceability → Every pattern maps 1:1 to specific FR/NFR.

No Microservices chosen yet (monolithic core is sufficient for Phase 1 scale; can evolve horizontally per NFR3).

5.2 Component Responsibilities & Interfaces

* Interaction Layer: Receives raw messages from WhatsApp (via Baileys bridge in dev/testing or webhook endpoint in production), detects language/hybrid, emits standardized “InboundMessageEvent”. The dual-mode adapter ensures all downstream layers receive identical event formats regardless of WhatsApp transport.
* Orchestration Layer: Routes events, manages sagas, schedules relances, handles queue/retry for blackouts.
* Business & Intelligence Layer: Applies Blueprint rules, generates responses, scores leads, triggers MAPS events. High cohesion: all persuasion lives here.
* Data Layer: Abstracts all persistence; ensures no lead duplication (NFR11).
* Observability Layer: Consumes MAPS events for dashboard; exposes audit endpoints; provides admin operations interface (bot configuration, escalation management, content management, system control) via role-gated Streamlit pages routed through FastAPI.

Communication Style:

* Synchronous only for <60 s critical path (first response).
* Asynchronous/event-driven for everything else (relance, MAPS, escalation) → achieves resilience and scalability.

High Cohesion / Low Coupling Achieved:

* Persuasion logic is isolated in its own module (easy to update Blueprint).
* Queue decouples channel from business logic.
* Data layer hides storage details.

Alignment with Quality Attributes:

* Scalability (NFR3): Horizontal scaling of Orchestration and Business layers.
* Maintainability (NFR7): Clear layer boundaries + defined interfaces.
* Performance (NFR1): Critical path kept short.
* Resilience (NFR2): Queue + saga compensation.

This logical architecture provides a solid, traceable foundation for detailed design, implementation (Phase 1 core flows), and future evolution (Telegram/web channels).

Approval Note

This High-Level Architecture is fully aligned with Requirements v1.1, Persuasion & Growth Blueprint, Use/Misuse Cases, and User Stories. It directly realizes “Structure as a Service” while mitigating all identified risks.

   - Persuasion engine (Cialdini + SB7 + ERRC + Hormozi)

7. **Hub CRM/Airtable** (External order system)
   - Order creation/tracking
   - Club points management
   - Inventory sync

8. **MBB HUB** (Phase 2 — CRM Replacement)
   - Replaces Airtable as primary CRM backend
   - Customer data sync, lead routing, order management
   - Club points and loyalty program management

   - Connected via MBBHubAdapter (Adapter Pattern)

9. **MBB BOX** (Phase 2+ — Inventory System)
   - Real-time product stock levels by city/zone
   - Dynamic pricing updates
   - Product catalog and availability checks
   - Connected via MBBBoxAdapter (Adapter Pattern)
   - Graceful fallback to static catalog if unreachable
   - **Why:** Existing system integration

**Communication Patterns:**

- **Synchronous REST:** FastAPI (webhook endpoints), Streamlit ↔ PostgreSQL
- **Asynchronous Queue:** FastAPI → Redis (Celery broker) → Celery Workers (blackout recovery, async tasks)

- **Periodic Tasks:** Celery Beat → Redis → Celery Workers (relance scheduling, exports)

**Key Domain Entities:**

1. **Customer**
   - Unique identifier: `phone_number` (WhatsApp identifier)
   - Attributes: `name`, `city`, `language`, `opt_out_flag`
   - Central actor in all interactions

2. **Conversation**
   - Represents a continuous interaction session
   - Maintains `context_state` (current topic, last question asked)
   - `status`: active, escalated, converted, dormant

3. **Lead**
   - Derived from Conversation once qualification starts
   - `score`: hot (ready to buy), warm (interested), cold (browsing)
   - `stage`: awareness → consideration → decision
   - `intent`: product inquiry, support, loyalty (Club)

4. **Message**
   - Atomic unit of communication
   - `direction`: inbound (from customer) / outbound (from bot)
   - `language`: detected language (Lingala/French/Swahili)

5. **Relance**
   - Strategic re-engagement attempt
   - `attempt_num`: 1, 2, or 3 (hard limit)
   - `value_hook`: personalized value proposition (e.g., "New 3m cable available")
   - `scheduled_at`: respects blackout hours, cultural timing

6. **MAPS Tag**
   - Structured intelligence capture
   - `category`: product_demand, silence_reason, conversion_trigger, language_usage
   - `pattern`: extracted insight (e.g., "Cable 2m requested by pros in Gombe")

7. **Lab Insight**
   - Aggregated MAPS patterns
   - Feeds product development and marketing strategy

8. **Order**
   - Conversion outcome
   - `payment_type`: mobile_money, bank_transfer, COD
   - Links to Hub CRM for fulfillment

9. **Payment**
   - Transaction record
   - `method`: Orange Money, Airtel Money, M-Pesa, cash
   - `provider`: external payment gateway identifier

**Relationships:**

- Customer **has** multiple Conversations (1:*)
- Conversation **contains** multiple Messages (*:*)
- Customer **becomes** Lead once qualified (1:1)
- Lead **triggers** Relances (1:*, max 3)
- Message **generates** MAPS Tags (1:*)
- MAPS Tags **are analyzed by** Lab to produce Insights
- Lead **converts to** Order (1:0..1)
- Order **fulfills via** Payment (1:1)

**Business Rules Embedded:**

- Relance: max 3 attempts per lead (hard constraint)
- Opt-out: once `opt_out_flag = true`, no further relances
- Language: auto-detected from first message, sticky per conversation
- MAPS: every message generates at least one tag (100% capture)

**Traceability:**
- Maps to FR3–FR8 (qualification, nurturing, conversion, MAPS)
- Implements Blueprint principles (StoryBrand journey stages)
- Satisfies NFR11 (data privacy: minimal fields)

## 7. Technology Stack Selection

This section follows a structured, 6-phase decision process to select an optimal technology stack that is fully aligned with the system's architecture, requirements, constraints, and quality attributes defined in previous sections.

### 7.1 Architectural Style Alignment

**Selected Architectural Style:** **Layered + Event-Driven Hybrid** (defined in Section 5)

**Imposed Constraints:**

1. **Layered Architecture Constraints:**
   - Clear separation between presentation (interaction), business logic, data, and observability layers
   - Technologies must respect layer boundaries (no data layer calling business layer)
   - Must support dependency inversion (repositories, adapters)

2. **Event-Driven Architecture Constraints:**
   - Asynchronous message passing required for resilience
   - Technologies must support message queuing and pub/sub patterns
   - Queue persistence required (survives restarts)

3. **Scalability Model:**
   - Horizontal scaling for business logic layer (stateless)
   - Vertical scaling acceptable for data layer (single master, Phase 1)
   - Must support containerization (Docker)

4. **Communication Patterns:**
   - Synchronous REST for critical path (<60s target)
   - Asynchronous queue for relance, MAPS, blackout recovery
   - WebSocket not required (WhatsApp is webhook-based)

5. **Deployment Model:**
   - Self-hosted (no cloud vendor lock-in)
   - Single-node deployment (Phase 1), multi-node ready (Phase 2)
   - Docker Compose → Kubernetes migration path

**Eliminated Technologies:**

| Technology | Reason for Elimination |
|------------|------------------------|
| Serverless (AWS Lambda, Google Cloud Functions) | Violates self-hosted constraint; not suitable for stateful conversations |
| GraphQL | Unnecessary complexity; REST is sufficient for WhatsApp webhook and CRUD operations |
| gRPC | Overkill for internal communication; adds complexity without clear benefit in low-bandwidth environment |
| NoSQL (MongoDB, Cassandra) | MAPS analytics require complex joins; PostgreSQL's ACID guarantees critical for payment transactions |
| MQTT | Not needed; WhatsApp API is HTTP-based, not IoT protocol |

**Architectural Compatibility Check:**
- ✅ Technology choices must support layered separation
- ✅ Must enable asynchronous event handling
- ✅ Must be containerizable
- ✅ Must support horizontal scaling

- Django Admin eliminated: adds ORM overhead, a second Python framework, and unnecessary complexity for <10 concurrent admin users
- React/JS eliminated: adds a second language to the stack, violating the single-language Python principle
- Acceptable single-user limitation (Lab/Toronto/Hub teams = <10 concurrent users)
- Admin write operations route through FastAPI endpoints (not direct DB access), maintaining security consistency

### 7.7 Stack Rationale Summary

**Why This Stack Solves the MBB ya Kin Problem:**

1. **<60s Response Time (NFR1):**
   - FastAPI: Async request handling
   - Redis: Sub-millisecond session cache
   - Claude: ~1-2s LLM latency
   - **Total:** 3–5s average response time (10x better than target)

2. **Blackout Resilience (NFR2, ASR):**
   - Redis AOF: Zero message loss during power outages
   - Celery worker queue: Graceful resume after reconnection
   - Docker restart policies: Auto-recovery
   - **Result:** 100% message preservation, <5min recovery time

3. **Cultural Proximity (NFR4–NFR5, ASR):**
   - Claude: Handles Lingala/French/Swahili hybrids naturally
   - Prompt engineering: Embeds Cialdini, StoryBrand, Hormozi principles
   - Streamlit audits: Weekly tone compliance checks by Lab
   - **Result:** "Helpful young Congolese friend" tone maintained

4. **MAPS Intelligence (FR8, ASR):**
   - PostgreSQL JSONB: Flexible tag schema
   - Full-text search: Pattern analysis across languages
   - Streamlit: Interactive exploration for Lab Team
   - **Result:** 100% interaction capture, actionable insights

5. **Scalability (NFR3):**
   - FastAPI: Horizontal scaling (3 replicas → 6+ as needed)
   - PostgreSQL: Vertical scaling + read replicas (Phase 2)
   - Docker → Kubernetes migration path
   - **Result:** Supports 10K → 100K messages/day growth

6. **Cost-Effectiveness (NFR6):**
   - Total: $180/month optimized ($2,160/year)
   - vs. Custom solution: All-Python stack reduces development overhead
   - vs. SaaS chatbot platforms: $500–1000/month (64–82% cost reduction)
   - **Result:** Budget-friendly for African market

7. **Self-Hosted (ASR, Constraint):**
   - 90% of stack runs on-premise (only WhatsApp/Claude external)
   - No vendor lock-in for core components
   - Data sovereignty (DRC privacy compliance)
   - **Result:** Full control, portable across VPS providers

### 7.9 Technology Stack Decision Log

**Decision ID:** TS-001  
**Date:** April 2026  
**Status:** ✅ **APPROVED**

**Key Decisions:**

1. **FastAPI over Django/Flask:** Async-native performance critical for <60s target
2. **Celery over n8n/Airflow:** Python-native task queue, lower resource usage, single codebase
3. **PostgreSQL over MongoDB:** MAPS analytics require SQL joins; ACID compliance for payments
4. **Redis over RabbitMQ/Kafka:** Dual-purpose cache+queue; simpler ops at current scale
5. **Claude over GPT-4:** Equal quality, 50% cost reduction, better Lingala/French handling
6. **Streamlit over Grafana/React:** Rapid prototyping, Python-native, acceptable for <10 users
7. **Docker Compose over Kubernetes (Phase 1):** Simpler ops, sufficient for single-node deployment

**Trade-offs Accepted:**

- Celery requires Redis broker (already in stack, zero additional cost)
- Claude API external dependency (vs. self-hosted LLM) → Better cost/latency trade-off
- Streamlit single-user limitation → Acceptable given user base size

**Risks Mitigated:**

- LLM vendor lock-in → Abstract client, maintain prompt templates separately
- Single-node bottleneck → Clear Kubernetes migration path for Phase 2
